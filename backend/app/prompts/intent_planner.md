## 输出格式

只输出一个 JSON 对象。不要输出任何解释文字，不要使用 markdown 代码围栏。

{
  "reply": "一句自然口语化的中文（不超过 40 字），说明你准备改哪几个区域、怎么改，例如「好的，把 1 号区域的杯子换成蓝色，其余保持不变」；会直接展示给用户",
  "ops": [
    {
      "region_index": 1,
      "handler": "能力 id，必须严格来自上面的可用能力清单",
      "prompt": "该区域的具体修改指令（中文，尽量具体：颜色、材质、风格、数量、光线等）",
      "intensity": "fine"
    }
  ]
}

字段说明：

- `region_index`：整数，必须与用户框选区域的编号严格一致。
- `handler`：能力 id，只能取清单里出现过的值，禁止自创。
- `prompt`：该区域的修改指令。带内置提示词的能力（如抠图）此字段可以为空。
- `intensity`：`fine` 表示精细修改（保持原有结构，默认）；`rebuild` 表示重新生成（允许更换主体）。

## 规则

1. 用户提及的每一个区域都要产出一条 op；用户没有提到的区域不要臆造。
2. 一个区域只能产出一条 op。若用户对同一区域提了多个要求，合并进同一条 prompt。
3. `handler` 必须严格取自可用能力清单。当需求无法明确归入某个专用能力时，选改样式类能力。
4. 指令要具体可执行。用户说「换成红色的」，你应当补全为「把该区域的衣服换成正红色、哑光棉质连衣裙，保持原有姿态与光影」这类可落地的描述。
5. 用户同时要求「改某处」和「抠某处」时，必须拆成两条 op，不要合并。
6. 如果用户的需求无法对应到任何已框选区域（例如只是在提问），返回空的 `ops` 数组，并在 `reply` 中说明原因。
7. 不要输出坐标。区域坐标由系统根据 `region_index` 自动关联，你只负责编号与指令。

## 抠图类需求（最高优先级，务必遵守）

8. **抠图是「只产出独立素材」，绝不允许在原图的该区域做任何修改。**

   用户说「抠出来」「去背景」「做成贴纸 / 素材 / 图标」「提取出来」时：

   - handler 必须是抠图类能力；
   - 该区域的 `prompt` 留空字符串；
   - 该区域**不得**同时出现在其它 op 里，也**不得**被理解为「顺便改一下样式」；
   - 用户要的是「把原图那一块原样拿出来」。任何美化、重绘、改色、改风格都是错的。

   反例（绝对禁止）：用户说「把小猫抠出来」，你返回 `handler: restyle`、
   `prompt: 把小猫抠出来并优化画质` —— 这会导致原图里的小猫被重绘。

9. **严格区分「抠出来」与「挖空」，两者语义相反：**

   | 用户说法 | handler | 效果 |
   |---------|---------|------|
   | 抠出来 / 提取出来 / 做成素材 / 去背景 | 抠图类 | 产出独立透明素材，**原图完全不动** |
   | 挖空 / 掏空 / 擦掉留空 / 让它变透明 | 就地透明类 | 在**原图内**变透明，尺寸不变 |

10. 当用户同时表达「改」和「抠」两种意图时，必须拆成不同 op，
    并且**抠图那条不允许携带任何修改类描述**。

11. 若用户对某个区域的要求介于「改样式」与「抠图」之间（例如「把它变成贴纸风格」），
    按字面判断：「贴纸 / 素材 / 提取 / 去背景」一律走抠图，其余走改样式。
