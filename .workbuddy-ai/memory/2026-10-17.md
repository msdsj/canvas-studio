## 选区局部编辑编排（对标 lovart.ai）

用户诉求：图片编辑要支持「框选多个区域，部分改样式、部分抠成透明素材」，
且**能力不能写死**（不同用户场景差异大），要能智能分析自然语言需求。

### 关键设计决策

1. **能力注册表 + 意图分析**（而非硬编码动作枚举）
   - `edit_handlers.py`：内置 restyle/cutout/transparent/remove/enhance，
     管理员可通过配置 `EDIT_HANDLERS`（JSON）**纯声明式追加能力，零代码改动**；
   - `plan_service.py`：LLM 从注册表**动态生成能力清单**，把自然语言解析为 Intent DSL。
   - 结论：新增能力 = 加一条声明。执行代码不动。

2. **抠图必须本地做，不能走上游文生图**
   - 上游会重绘像素，而用户要的是原图那个区域的内容；
   - `cutout_service.py` 三级策略：rembg（可选）→ cv2 GrabCut（可选）→ 纯 Pillow chroma 兜底；
   - 本机只有 Pillow，实际走 chroma（边缘采样背景色 + 自适应阈值 + 形态学 + 羽化 + trim）；
   - 健壮性：前景占比 <1% 回退为纯选区裁剪，绝不交付空白素材。

3. **产出规则**：整图类合并成 1 张（上游只调一次，省钱），素材类每区域 1 张；
   混合 = 1 张整图 + N 张素材，顺序「先整图后素材」。

4. **计费**：只对 engine=upstream 的能力计费，纯抠图/挖空 cost=0。

### 踩坑记录

- **`run_task` 返回值格式不统一**导致 4 个原有测试挂掉：
  生成分支仍返回网关原始格式 `{data:[{b64_json}]}`，而新版 run_task 期望 `{images:[bytes]}`。
  修法：生成分支统一转换后再走公共落库逻辑。教训——重构公共出口时要同步所有入口的契约。
- `sed -i ''` 在本机 zsh 下报 "No such file or directory"，改用 Edit 工具替换更稳。

## 第二轮：用户反馈「少了一张图没抠出来」→ 定位并修复

### 根因（两个问题叠加，缺一不可）

1. **后端进程跑的是旧代码**：`/api/generate/capabilities`、`/api/generate/plan` 路由
   在 openapi.json 里都不存在 → 旧版 `/edit` 不认 `ops` 字段，只认旧的 `region`，
   所有区域一律按兜底能力（改样式）处理 → 只产出 1 张。
   **uvicorn 未带 `--reload`，改代码不会自动生效。**
2. **前端只投递 `result_urls[0]` 却标记任务「已投放」**：
   `WorkspaceView` 的 `tick`（占位骨架主路径）只投第一张，而 `placeResults`（兜底）
   会遍历全部；主路径投完第一张就 `markTaskPlaced`，兜底逻辑据此跳过 → 其余结果永久丢失。
   改动前一个任务永远只有一张产出，所以这个 bug 一直潜伏。

### 修复

- 抽出模块级 `placeTaskResults()`，两条路径统一走它，逐张投递 + 按自身宽高比缩放
  （只缩不放，最大边 320）+ 横向 40px 间距；
- 新增 `imageSize()` 读图片真实尺寸，避免素材被强行拉成正方形；
- ChatPanel「加入画布」同样遍历全部 urls，WorkspaceView 侧用游标错开位置；
- 附带：提示词意图自动识别（写「抠出来/去背景」→ 自动切到抠图能力，用户手动选过的不再改写）；
  本地处理类能力的输入框改为「可选」并标「本地处理」标签（此前会被整块替换、用户输入突然消失）。

### 验证（真实环境，非 mock）

重启后端（PID 11904 → 72453，路由 69 → 71）后提交 `ops=[restyle, cutout]`：

```
结果张数: 2
  [1] PNG RGB  (256, 256)                    ← 完整修改图，与原图同尺寸
  [2] PNG RGBA (70, 70) alpha范围=(0, 255)   ← 透明素材，尺寸收紧到主体包围盒
```

后端 120 passed，前端 tsc 通过。

### 重要教训

- **重构公共出口必须逐个核对所有入口的契约**。多产出引入后，「只投第一张」从无害变成数据丢失，
  类型检查和单测都拦不住，只能靠「新增能力 → 审查所有消费点」。
- **部署步骤是功能的一部分**。后端未重启时前端新参数被静默忽略，表现为「代码明明写了却不生效」。
  排查此类问题最快的手段：查 `openapi.json` 里新路由是否存在。

## 第三轮：用户反馈「要抠出来的地方在原图上也被改了样式」

### 根因（三层）

1. **标记图给全部区域画了红框**：前端 `buildEditPayload` 用全部 regions 绘制 mask，
   上游收到「3 个红框 + 只说 1、2 怎么改」的图，会把区域 3 也改掉。**这是设计缺陷**。
2. **意图识别不精准**：只靠前端一份本地关键词表，覆盖有限，没命中就按默认「改样式」提交。
3. **兜底计划覆盖用户选择**：对话模型不可用时后端返回全 restyle 的兜底计划，前端不加区分地应用，
   把用户手动选的 cutout 冲掉。

### 修复

- **后端自绘标记图** `_render_region_mask()`：只标注 `engine=upstream` 的区域，
  带 ops 时忽略前端 mask；编号沿用原始序号（跳过某区域也不错位）。前端 `markIndexes` 同步。
- **接入对话模型做意图分析**：编辑层「AI 分析」按钮 + **提交前自动复核**；分析过程可见
  （按钮/生成按钮显示「分析中…」+ 输入区文案）；失败不阻断，退回手动设置。
- **提示词硬约束**：`intent_planner.md` 新增「抠图类需求（最高优先级）」章节；
  handler description 强化并互相点明「抠出来 vs 挖空」的相反语义。
- **demo 兜底不覆盖用户选择**：前端检测 `plan.demo === true` 时跳过应用并提示。

### 验证（真实环境）

3 区域（2 restyle + 1 cutout）：上游返回 2 张；产出1 抠图区中心像素
`(215,35,35)` = 原图红色**未被改动** ✓；产出2 PNG RGBA 70×70 alpha(0,255) ✓。

新增 4 项单测（标记图排除本地区域、编号不错位、3 区域保真、上游乱改也还原）。
后端 **124 passed**，前端 tsc 通过。

### 关键设计结论

**「不许改」不能只写在提示词里，必须落到像素上。** 三层防护：
① 提示词约束（降低误改意愿）→ ② 标记图只圈上游区域（消除视觉误导）
→ ③ 合成阶段按选区还原（上游乱改也还原）。**只有第 ③ 层是确定性的。**

所以分析走兜底（UI 会提示「AI 分析暂不可用」）。在后台系统配置页填入可用的

## 第四轮：用户指出架构方向错误 → 按「一切走上游 + 并发」重构

### 用户原话要点
「我全部的图片操作都是需要去把图片和文字提示词给到 gpt」
「裁剪啥的全部的操作其实你是需要走图片中转站去生成图片」
「如果要搞多张图片你需要考虑到并发」
「我框选的地方你好像一直都没有精确啊」

### 找到三个真实缺陷
1. **mask 用错（框选不精确的确定根因）**：传给上游的是**不透明的红框标记图**，
   而 OpenAI `images/edits` 的语义是「透明=修改、不透明=保留」。
   传全不透明图 = 告诉上游「整张图都要改」，位置完全失控。
2. **抠图方向错**：用户要走上游，我做了本地 Pillow 处理。
3. **无并发**：多区域串行调用。

### 重构
- **每区域并发单独调用**（`_call_upstream_regions` + Semaphore，上限 `EDIT_CONCURRENCY`）
- 每次调用三件套：纯原图 + **单区域**引导图 + **标准 inpainting 掩码**
- `cutout` engine: local → **upstream**（带内置提示词，前端不再强制填指令）
- **抠图透明兜底** `CUTOUT_LOCAL_FALLBACK`：实测中转站会丢 alpha，自动本地补
- 计费改为 `edit 单价 × 上游区域数`
- 用户自己也改了代码：新增 `guide`（引导图）、`TEXT_API_*` / `LLM_BASE_URL` 独立通道
  —— 这些改动我都保留并整合，没有覆盖

### 验证（真实环境）
- 3 区域：成本 24（=8×3）、日志确认 3 条并发请求、产出 1+1、抠图区原样 ✓
- 透明兜底：上游返回不透明 → 兜底后 alpha(0,255) 真透明 ✓
- 后端 131 passed，前端 tsc 通过

### 修的中转站配置
- `TEXT_API_BASE_URL` 缺 `/v1` → 裸域名返回网页 HTML
- `INTENT_PLANNER_MODEL` = `gpt-4o-mini` 不被支持 → 改 `gpt-5.4-mini`
- 该中转站当时持续 429 限流，意图分析实际效果待恢复后确认

### 环境教训
本机**无法长期保持后台服务**：nohup / run_in_background 启动的进程都会被回收。
而且我一开始 kill 错了 PID（以为是自己启动的），导致「改了代码却不生效」排查了很久。
**正确姿势**：先 `lsof -nP -iTCP:<port> -sTCP:LISTEN -t` 拿到真实 PID，再 kill；
验证代码是否生效看 `openapi.json` 新路由 + 接口返回的新字段。

## 第五轮：简化回「一次调用 + 标注图」（用户明确要求）

用户原话：「我框选了两个地方，你就用画笔或边框包起来，提交给 GPT 的时候把我这张
用边框线或画笔处理的图片丢过去，给 AI 的是包含两个需求的提示词和这张有涂鸦的图片，就这么简单。」

**上一轮的「按区域拆分并发 + inpainting 掩码」是过度设计，已回退。**

最终架构：
- 一次编辑 = **1 次上游调用**（合并所有改样式区域的分点指令）
- 传 `image①` 底图（原图+涂鸦）+ `image②` 引导图（原图+涂鸦+编号框）+ `prompt`
- 结果只贴回选区，选区外逐像素保留原图
- **抠图不送上游重绘**：从原图精确抠出（保证「原样拿出来」），不计费
- 就地挖空：上游生成 + 本地 alpha 收口

**关键教训**：用户要的是「一张标注图 + 一段提示词」，不是复杂的区域编排。
遇到模糊需求时，先问清「提交给上游的是什么」比埋头设计架构更重要。

用户还把 `transparent` 改成了 upstream（本地只做 alpha 收口），已按此调整：
`_apply_transparent` 的判断改为 `executor == "transparent" or id == "transparent"`。

验证：131 passed（编排测试 35 项）。前端 tsc 通过。

## 「生成出来是 DEMO 图」排查（16:00）

用户上传截图：结果图是一张白底、红字 `CANVAS STUDIO · DEMO` + 自己提示词的占位图。

**结论：不是 AI 画的，是 gateway 的 demo 降级占位图。**

链路：
1. `CS_DEMO_MODE=auto`（`.env:34` + `system_configs.DEMO_MODE=auto`）
2. 生图上游 = `http://127.0.0.1:3000`（本地 chatgpt2api，Docker）
3. 直接打上游 `POST /v1/images/generations`（model=gpt-image-2）→ **429 `no available image quota`**
   （模型名是对的；同端点换 gpt-5-6 会报 unsupported image model，说明它只认 gpt-image-2 系列）
4. gateway `image_router.py` 旧逻辑：`except GatewayError` 时 `if mode == "auto": return demo_image_result(...)`
   → 任何业务错误（含没额度）都变成"成功 + 占位图"

另一条路也不通：中转站 `fast.msdsj.site` 用现有 key 调生图 →
**403 `Image generation is not enabled for this group`**（该分组未开通生图，虽然 /v1/models 里能看到 gpt-image-1/1.5/2/2.5）。

**已改**：
- `gateway/app/services/image_router.py`：只有 `PROXY_UNREACHABLE`（根本连不上）才降级；
  号池无额度/鉴权失败/限流/5xx 一律如实失败并退款。生图与图片编辑两处都改了。
