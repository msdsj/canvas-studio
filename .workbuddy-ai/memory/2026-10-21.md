## 空闲 CPU 优化（未提交改动）验收：结论是「收益几乎为零」，且踩了两个测量陷阱

承接 HEAD 上已有的未提交改动（CanvasMinimap / CanvasNavigator / WorkspaceView 视口签名 /

### ★ 最重要的一条：先前「CPU 从 25.7% 降到 3.6%，快 7 倍」的结论是错的
那个数字是在 `/onboarding` 页面测的。原因：`admin@canvas.studio` 的
`onboarding_completed_at` 为 null，访问 `/workspace` 会被重定向到引导页，
探测脚本只 sleep 固定时间、**不校验落地 URL**，于是把引导页当成了工作台。
→ 已 `/api/onboarding/complete` 完成引导；**探测脚本必须校验 `location.href` 与关键 DOM**。

### 真实结论（零注入，稳定态，各 3 次，交替 A/B）
| 场景 | 基线 HEAD | 本次改动 | 差异 |
|---|---|---|---|
| 空闲 8s | 5.3% / 5.4% / 5.3% | 5.3% / 5.4% / 5.6% | 无（在噪声内） |
| 连续缩放 6s | 14.1%（script 309ms） | 14.1%（script 306ms） | 无 |

**为什么没收益**：原版 CanvasMinimap / CanvasNavigator 虽是常驻 rAF，但「场景签名没变就直接
return」，静止时只有取元素 + 拼签名的浅成本；真正的大头是 GSAP ticker、ScrollTrigger
`_rafBugFix`、Excalidraw `AnimationFrameHandler` 三支本来就该常驻的循环。所以这次改动
**语义上更干净（有变化才画、onChange 订阅），但没有可测的 CPU 收益**。

### ★ 测量陷阱（两个，都会得出反向结论）

   且单文件二分时「还原任一文件都是 13%」是假的——那是 HMR 抖动，不是代码问题。

### 核心实测结论（务必记住）
1. **连接池越大越慢**（反直觉，已多次复现）：
   - `pool=2` → 32 并发 **1696 req/s**，p50 18.8ms
   - `pool=20` → 16 并发 **462 req/s**，p50 35.7ms ← 慢 3.7 倍
   - 原因：aiosqlite 每条连接 = 一个独立 worker 线程，执行靠「事件循环↔线程」投递；
     连接数≈并发数时请求全在等线程唤醒。**要更高吞吐请加进程，不要加连接。**
2. **性能分层归因**（16 并发，`/api/generate/tasks`）：
   - 纯 SQL（进程内）1500 /s → +Pydantic 900 /s → 真实 HTTP 557~650 /s
   - 纯 HTTP 上限（`/api/health`，不查库）1167 /s
   - 结论：业务层已接近单个事件循环的极限，剩余差距在 ASGI 序列化，不是 SQL 写法问题。
3. **复合索引杀掉临时排序**：加之前三条读路径全 `USE TEMP B-TREE FOR ORDER BY`；
   加 `(user_id, created_at)` 与 `(user_id, status, created_at)` 后全部消失。
   32 并发 p95 从 83.1ms → **29.5ms（-64%）**。
   `list_unread` 原本误用 `status` 单列索引 → **扫全库所有用户**，现已修正。
4. **认证查询不值得优化**：`select(User)` 实体化 vs 只取列，实测都是 0.32ms（1.00x）。
   做归零实验才发现的，别在这上面花时间。
5. 前端真实负载：`useActiveTasks` 每 3s 打 `/api/tasks/active`、每 6s 打 `/api/tasks/unread`。
