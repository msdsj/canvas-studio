## B. 交互规则（工程可直接落地）

1. 当 `e.nativeEvent.isComposing === true` 或 `e.keyCode === 229` 时，**必须**直接 return，**禁止**调用 `preventDefault` 与 `onSend`。
2. 当 `!e.isComposing && e.key === 'Enter' && !e.shiftKey` 时，**必须**先 `preventDefault`，再判断 `value.trim()`；为空时**禁止**发送，**必须**保留换行行为（不要吃掉按键）。
3. 当用户设置"Enter 发送"关闭时，**必须** Enter 换行、`Ctrl/Cmd+Enter` 发送；该开关**必须**持久化到 localStorage，并在输入框下方以 caption 常显当前快捷键。
4. 当 `content` 经 `trim()` 后为空，或剔除 `\u200B\u200C\u200D\uFEFF\u00A0` 与纯 emoji 后为空时，**必须**禁用发送按钮并给出内联提示，**禁止**仅在 onClick 里静默 return。
5. 当 `submitting === true`（从点击到 `await generateApi.image` resolve）时，**必须**禁用发送按钮并切换为 loading 态，**禁止**接受第二次提交。
6. 当幂等键作用域构造时，**必须**包含 `prompt` 归一化哈希（如 `image:${sessionId}:${hash(prompt)}`），**禁止**只用 sessionId。
7. 当后端返回 `created === false`（replay）时，**必须**给出明确提示"这次提交与 N 秒前的请求相同，已复用原任务"，**禁止**静默清空输入。
8. 当输入内容非空时，**必须**在 `sessionStorage` 保留草稿（按 sessionId 分键），页面重载后恢复；发送成功后才清除。
9. 当 `messages.length` 或 `tasks.length` 变化时，**必须**先判断视口是否距底 < 80px，是才自动滚底；**禁止**无条件 `scrollTop = scrollHeight`。用户上滑后**必须**出现"回到最新"悬浮按钮。
10. 当任务 `status` 为 `queued`/`running` 时，**必须**只提供「停止生成」一个破坏性操作（直连 cancel，真退款），**禁止**同时出现「暂停」与「放弃」；当 `status === 'queued'` 时，**必须**显示位次（第 N 位 / 前面还有 M 个）。
11. 当用户已有 N 个活跃任务且 N ≥ 上限时，**必须**在发送前拦截并展示"2/2 进行中，可等待或放弃其一"，**禁止**只依赖 429 toast。
12. 当任务 `status === 'failed'` 时，**必须**在消息流原位置内联"重试"按钮，点击**必须**直接用原 prompt 发起新任务；**禁止**把 prompt 塞回输入框冒充重试。
13. 当渲染错误时，**必须**只展示人话文案 + 下一步动作（重试 / 联系管理员 / 换提示词），**禁止**展示 `error_code` 等英文枚举。
14. 当任务失败/超时时，**必须**在原位置标注"额度已退回"，**禁止**让用户自行猜测是否扣费。
15. 当 `succeeded` 结果出现时，**禁止**自动加入画布；**必须**停留在安全区并给角标计数。用户手动"加入画布"后，该图**必须**从安全区标记为"已放入"并置灰，**禁止**可重复点击造成重复落图。
16. 当同一任务有 1 张结果时，**必须**单列大图（宽度 100%）；2 张两列；3-4 张两列；5-9 张三列。**禁止**固定两列。
17. 当消息流含生图请求时，**必须**把用户 prompt 作为一条 user 消息写入时间线，任务卡挂在该消息之后（按 `created_at` 统一排序），**禁止**把所有任务堆在消息区下方。
18. 当焦点需要被抢占时，仅限：画布框选完成、点击"重新生成"、切换会话后恢复草稿；**禁止**在任务轮询刷新、toast 弹出、消息到达时抢焦点（否则用户正在输入的内容被打断）。
19. 当提示词超过 2000 字时，**必须**显示字数并禁止提交（前端计数 + 后端校验同值）；**禁止**静默截断。
20. 当内容被安全策略拦截时，**必须**给出改写建议（"试试去掉人物姓名/品牌词"），**禁止**只回"内容不合规"。

## E. 最该先做的 5 件事（按用户感知强度）

1. **修幂等键作用域（P0）**——同一会话 5 分钟内只能产出一张图（换 prompt、换参数都命中同一键），输入还被清空。这是"功能不可用"级别，每次连续创作都会撞上，用户会认为"AI 没听懂我说什么"。改动最小（键的作用域 + 生命周期）、感知最强。
2. **回车规则 + isComposing（P0）**——中文用户第一次用就会误发消息，直接把"专业感"打没。同时补 in-flight 锁，避免修好幂等后暴露双扣费。
3. **拆掉自动落画布，恢复安全区语义（P0）**——当前画布会被自动塞图、点一次又多一张。安全区是产品差异化的核心承诺（"不砸乱你的画布"），现在被自己的兜底逻辑推翻。修复不是加守卫，而是**取消自动投放**：安全区仍是 196px 交互缩略图（点击即把那一张放进画布，这是它的核心价值），只是不再自动往画布塞图。同时把去重从 task 级改成 url 级（否则多图任务只放一张就误标已投放，剩余 N-1 张永不补投），并统一两个入口语义（结果卡的「加入画布」放该任务下所有未投放的 N 张，安全区点击只放被点的那 1 张）。
4. **进度表达从"假百分比"改成"不确定 + 分级安抚"（P1，但并入批次 1）**——30% 冻结最长 180s（F3 落地后是 330s）是最容易被判定为"卡死"的形态。后端只有 30 一个值，任何百分比都是撒谎。档位记 P1（不阻断、不损失、可自愈），但它是 P0-A 的触发器（用户以为卡死 → 重发 → 被幂等吞掉），且修复成本是"删一个组件 + 加两行文案"，因此不得排到批次 2。
5. **时间线统一 + 生图 prompt 进消息流（P1）**——现在用户的话在时间线里消失，只剩一个截断 40 字的卡片标题堆在底部。这是"对话式创作"产品的骨架，不修则整个交互叙事不成立；顺带补时间戳、复制、原地重试。

## F. 产品口径裁定（回应 qa-lead 的两个语义问题）

QA 提出的「暂停」与「重试」不是 bug 修复问题，是产品承诺与实现不一致。以下是裁定，工程按此落地即可，不再讨论。

### F1 「暂停」本期改为「停止生成」，paused 状态前端不可达

**事实核对**（全部成立）：
- `task_service.py:208-217` pause 只改状态，注释自己写着"不强行中断上游"
- `generate.py:303-304` resume 会再次 `run_task`，而原始后台任务仍在 `await` 上游（`config.py:86` gw_read_timeout=300s）→ **两条并发跑同一任务**
- 并发后果链：① 双份上游调用，双烧号池；② `generate_service.py:235-246` 在 `succeed()` 之前就落库，两条各落一套资产 → **多一份永久孤儿**；③ `mark_progress(30)` 被第二条重置 → 进度可能从 100% 倒回 30%；④ 第一条 succeed、第二条早退（`task_service.py:276-277`）→ 状态对但资产重复
- `task_service.py:318-337` reclaim_orphans 在 180s 把 paused 判 timeout 并退款 → 用户看到"已超时"

**本期口径（不做状态机删除，走止血退路）**：
- 按钮文案「暂停」→「停止生成」，直连 `cancel`（`task_service.py:232-245`，真退款）
- `paused` 状态保留在后端，但**前端不再可达**：不做入口、不做恢复
- "删除 paused 状态与 resume 接口"列入下一迭代，见 G 节

**理由**：上游是同步长请求，没有真正的挂起/续接能力。用户点"暂停"的唯一真实诉求是"别再烧了"，而这个诉求只有取消能满足。保留"暂停"= 假承诺 + 孤儿资产 + 双份资产 + 额度冻结。而删状态机属于范围变更，本期用"改名 + 改指向"即可消除全部用户可见损害。

**「额度已退回」这句文案已验证可用**，不必降级为"已停止"：`task_service.py:232-245` 的 cancel 调用 `quota_service.refund`，而 `quota_service.py:100-122` 对 `processing` 流水真实加回余额、已 `success` 的拒绝回滚、重复调用幂等；任务已终态时 cancel 直接抛 `TASK_STATE_CONFLICT`（`:235-238`），不会出现"已成功却提示退回"的假承诺。

**规则**
- 当 `status ∈ {queued, running}` 时，**必须**只出现一个主操作「停止生成」，**禁止**出现"暂停"。
- 当用户点「停止生成」时，**必须**二次确认并说明后果："停止后本次不扣额度，已画出的画面不会保留"，**禁止**静默执行。
- 当停止成功时，卡片**必须**变为「已停止 · 额度已退回」，主按钮变「重新生成」，**禁止**保留"继续"。
- 当读到历史 `paused` 任务时，前端**必须**按「已停止 · 额度退回中」呈现并给「重新生成」按钮，**禁止**渲染成"已暂停"死卡（无按钮会让用户以为界面坏了），**禁止**暴露"继续"。
- 当未来上游支持真异步任务（可凭 `upstream_task_id` 续接）时，才允许重新引入"暂停"，届时语义**必须**是"不再等待、结果仍可落地"。

**⚠️ 后端依赖（前端隐藏按钮不足以闭环）**：`task_service.py:31-32` 中 `ACTIVE_STATUSES` 含 paused、`CONCURRENCY_STATUSES` 不含 paused，而 `count_active()`（`:57-65`）与 `reclaim_orphans()`（`:322`）都只扫 `CONCURRENCY_STATUSES`。后果有两条：
1. **paused 任务永远不会被回收**——不超时、不退款、不清理，一直出现在 `/api/tasks/active` 轮询结果里，用户每开一次页面就多拉一批僵尸任务；
2. **paused 不占并发配额**——用户可借"暂停"腾出并发槽位，而上游可能仍在跑，形成资源占用漏洞。

同时 `_TRANSITIONS["paused"]` 仍含 `"running"`（`:24`），所以 `resume` 接口（`generate.py:294-305`）对历史 paused 任务**仍然合法可用**——"前端不可达"只是隐藏了入口，API 层面并没有关。因此本期**必须**至少做一件事：把 paused 纳入回收扫描（或做一次性 `paused → cancelled` 迁移），并删除 `_TRANSITIONS["paused"]` 中的 `"running"`。仅靠前端映射会让僵尸数据永久累积。

### F2 「重试 / 再生成」必须真的发请求

**事实核对**：`ChatPanel.tsx:169-175` 两个 handler 都只有 `setInput(task.prompt)`；`handleRetry` 还额外弹 `toast.info('重试')`，且不聚焦输入框 → 用户点完视觉上毫无变化，以为在重跑。

**裁定**：真发。每次点击创建新任务（新幂等键），卡片原位替换为新任务进度。
**规则**
- 当 `status ∈ {failed, timeout, cancelled}` 时，「重新生成」**必须**直接用原 prompt 创建新任务，按钮**必须**进入 loading 直到新任务出现在列表。
- 当 `status === 'succeeded'` 时，「再生成一张」**必须**同样创建新任务（允许同 prompt 多次出图），**禁止**复用旧幂等键。
- **禁止**把 prompt 塞回输入框冒充重试；**禁止**用 toast 宣告"重试"而不发请求。
- 若本期确实不做真发，文案**必须**改为「填入提示词」，并**必须** `focus()` 输入框，**禁止**继续使用"重试/再生成"字样。

### F3 生成结果不得被系统自己判为失败（本期 P0）

**事实核对**：`config.py:83` task_timeout_seconds=180 < `config.py:86` gw_read_timeout=300。任何 180-300s 的生成会被 reclaim 判 timeout 并退款（`task_service.py:318-337`），上游随后返回成功时 `succeed` 早退（`:276-277`），而资产已经落库（`generate_service.py:235-246`）→ 用户看到"已超时"，系统里多一张没人认领的图。**是我们自己的配置把成功判成了失败。**

**产品表述**：生成结果不得被系统自己判为失败。用户看到的终态必须是"这次生成真的失败了"，而不是"我们没等到"。

**规则**
- 当设置超时阈值时，**必须**满足 `task_timeout_seconds ≥ gw_read_timeout + 30`（即 ≥330s），**禁止**小于上游读超时。
- 当任务耗时 < 180s 时，**禁止**在界面上出现"超时"字样，**必须**显示"仍在生成"。
- 当回收判超时前，**必须**先确认上游请求已失联（进程重启/连接断开），**禁止**仅凭 `last_activity_at` 判定仍在 `await` 中的任务——否则调阈值只是把误杀窗口推后，根因仍在。

### F4 幂等键 = 一次用户动作，不是一次会话

**事实核对**：`ChatPanel.tsx:126-128` scope 只有 `image:${sessionId}`——**不含 prompt，也不含 quality/size/n**；键持久化在 localStorage（`task-persistence.ts:45-58`）；后端 300s 内同键直接 replay，且**只查 key 不比对 payload**（`task_service.py:88-93`）。

**升级后的严重度**：这不只是"同一 prompt 重发被吞"，而是**一个会话在 5 分钟内只能生成一张图**——换任何提示词、换任何尺寸/质量参数，全部命中同一个键。叠加 `resetKey` 只在 catch 里调用（`ChatPanel.tsx:136`），只要成功过一次，键就永久粘住。

修复时必须一并验证 `task_service.py:92` 的 `existing.status in ACTIVE_STATUSES` 分支：窗口过期那一刻若上一任务仍是 running/paused，仍会继续 replay 而不换键 → 会出现"有时能发、有时不能发"的玄学复现。

**裁定**：幂等的目的是"防止同一次提交被重复执行"，不是"对内容去重"。键的生命周期 = 一次点击（含该次点击内的网络自动重试）。
**规则**
- 当用户点击发送时，**必须**生成一次性新键，仅在该请求的网络重试中复用，**禁止**跨主动操作复用、**禁止**持久化到 localStorage 供下次使用。
- 当需要防"手抖双提交"时，**必须**用 in-flight 锁（前端禁用 + 请求期间不可再发），**禁止**用长期持久化键代替。
- 当用户用同一 prompt 再次提交时，**必须**产生新任务（"同提示词再画一张"是合理且高频诉求）。

### F7 落图语义：按 url 去重，取消自动投放（P0-B 定稿）

**现状证据**：`WorkspaceView.tsx:537-554` 手动落图只调 `markTaskPlaced(taskId)`，标记粒度是 **task 级**（`task-persistence.ts:97-108` 存 `cs.autoPlacedTasks`，元素为 `task.id`）；自动侧 `:580` 用 `!isTaskPlaced(task.id)` 过滤。于是两个缺陷互为镜像：
- **重复**：手动侧不判 placed → 自动落图先跑、用户再点一次 → 画布两张（`:538` 入口无守卫）
- **漏投**：手动侧标了 task 级 → 多图任务只点一张，整任务被判已投放 → 剩余 N-1 张永不补投

**裁定（本期）**
- 落图去重粒度改为 **url 级**，判定键 = `task_id + url`，同一任务的多张图各自独立。
- 两个入口语义统一：任务卡「加入画布」= 批量投放该任务下**所有未投放**的 url；安全区点击 = **只投放被点的那一张** url。
- 已投放的 url **必须**置灰 + 文案「已放入」，**禁止**再次点击产生新元素。
- 任务级 `isTaskPlaced` **仅**用于"该任务是否已全部投放"的展示判断，**不得**作为投放拦截依据。
- 自动落图入口**本期移除**（安全区承诺优先），只保留任务卡与安全区两个手动入口。
- **取消的是"自动投放"，不是"投放能力"**：安全区仍是 196px 交互缩略图，点击仍然把那一张放进画布（这是它的核心价值：用户自己决定放哪张）。因此画布列宽度不变、断点表不动。

**配套规则（移除自动投放的必要补偿，不是可选优化）**
- 当任务成功时，**必须**出一次 toast：「生成完成，N 张已放入右侧结果区」，**禁止**静默完成——否则用户不知道结果到了，会把"没自动进画布"当成"没生成出来"。
- 当安全区处于折叠态时，**必须**用角标显示未读张数（`ResultDock.tsx:81-85` 已有计数，需补未读态）。
- **禁止**恢复顶部「N 个新的生成结果」常驻横幅（`UnreadResultsBanner` 工作台未挂是刻意为之：上一轮用户明确要求移除，理由是常驻遮挡画布）。发现性只靠 toast + 折叠态角标两个轻量通道。
- 当失败卡被「重新生成」原位替换时，新任务卡**必须**使用新 taskId 作为渲染 key，**禁止**继承旧卡的 placed/未读状态（否则「已放入」徽章会残留到新卡上）。
