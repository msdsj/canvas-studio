# 软件开发团队协作规范与交付流程

> 项目：canvas-studio —— 对标 Lovart.ai 的 SaaS 类 AI 创作平台
> 团队：software-canvas-studio · 主理人：齐活林（交付总监）
> 版本：v1.0 · 2026-10-16

---

## 1. 团队编制与职责边界

| 角色 | 成员 | 职责 | 专属交付物 | 路径 |
|------|------|------|-----------|------|
| 交付总监（主理人） | 齐活林 | 需求受理、流程编排、信息中转、质量门禁裁定、交付汇总 | 协作规范、交付总结报告 | `docs/00-team-workflow.md` |
| 产品经理 | 许清楚 | 需求分析、PRD、UI 设计规范与设计稿 | PRD + 设计规范 + HTML 设计稿 | `docs/01-prd.md`、`docs/01b-ui-design.md`、`docs/design/` |
| 架构师 | 高见远 | 系统架构设计、技术选型、任务分解（含依赖图与实现顺序） | 架构设计文档 + 任务列表 | `docs/02-architecture.md` |
| 工程师 | 寇豆码 | 按任务列表批量实现代码、全局一致性自检 | 全部源码 | `frontend/`、`backend/`、`gateway/`、`deploy/` |
| QA 工程师 | 严过关 | 测试用例编写与执行、智能路由判定、回归验证 | 测试代码 + 测试报告 | `docs/04-test-report.md` |

### 核心铁律
1. **专业产出只能由对应角色输出**：主理人只做编排与汇编，不代写 PRD / 架构 / 代码 / 测试。
2. **顺序流转**：前一阶段交付物通过质量门禁后，才允许进入下一阶段。
3. **信息单通道**：所有跨成员信息流必须经主理人中转，成员之间不得直连。
4. **文档化**：每阶段输出落盘为 Markdown（编码前缀见 §6），供后续阶段与增量开发复用。

## 2. 工作流路由规则

收到需求时，首先按规模判断工作流类型：

| 场景 | 判定条件 | 工作流 |
|------|---------|--------|
| 小型需求 | 单页应用、小游戏、工具脚本、≤10 个源文件 | ⚡ 快速模式：主理人 → 工程师 → QA |
| Bug 修复 | 明确 Bug 报告，非新功能 | 🔧 BugFix 路径：主理人 → 工程师（定位+修复）→ QA（回归） |
| **中大型需求** | **多模块、前后端+网关、>10 个源文件** | **🏗️ 标准 SOP（本项目采用）** |
| 仅需分析 | 只要 PRD / 架构评审 / 调研 | 📋 部分工作流（仅调度相关成员） |

> 原则：宁选快速模式，不选过重流程。**本项目因涉及前端 + 后端 + 网关三组件整合，判定为标准 SOP。**

## 3. 标准 SOP 五阶段流程

```
需求受理 → ① PRD → ② 架构设计+任务分解 → ③ 代码实现 → ④ 测试验证 → ⑤ 交付汇总
         许清楚      高见远                寇豆码          严过关        齐活林
```

### 阶段 0 · 需求受理（主理人）
- 输入：用户需求原文 + 既有代码库勘探结论
- 动作：判断工作流类型 → 建立团队 → 落盘协作规范 → 制定任务清单
- 出口条件：团队建立、任务列表就绪

### 阶段 1 · PRD（产品经理 许清楚）
- 输入：原始需求 + 现有资产清单（三个既有项目的能力事实）
- 输出：PRD（产品目标 / 用户故事 / 需求池 P0-P2 / 功能详述 / 页面清单 / 待确认问题）+ 设计规范 + 关键页面 HTML 设计稿
- 出口条件（G1 门禁）：
  - [ ] P0 功能全集明确、可实施
  - [ ] 页面清单与角色权限矩阵完整
  - [ ] 设计规范含双主题色板值/组件规范
  - [ ] 无阻塞性歧义（若有，由主理人裁定默认假设并记录）

### 阶段 2 · 架构设计 + 任务分解（架构师 高见远）
- 输入：G1 通过的 PRD + 设计规范
- 输出（一次性）：
  1. 实现方案 + 框架选型
  2. 文件列表及相对路径（全部源文件）
  3. 数据结构与接口定义（类图/数据模型）
  4. 程序调用流程（时序图）
  5. **任务列表**（有序、含依赖关系、按实现顺序）
  6. 依赖包清单
  7. 共享知识（跨文件约定：命名/错误码/环境变量）
  8. 待明确事项
- 出口条件（G2 门禁）：
  - [ ] 每个 P0 需求都可追溯到至少一个文件/接口
  - [ ] 任务列表可直接派发给工程师，无需二次设计
  - [ ] 集成接口（chatgpt2api 生图 / sub2api 对话）的对接契约明确

### 阶段 3 · 代码实现（工程师 寇豆码）
- 输入：G2 通过的架构设计 + 任务列表
- 动作：按任务列表**批量编写代码**（同模块文件一起写）
- 质量门禁（G3）：
  - [ ] 全部文件完成后执行**全局一致性审查**，输出 `IS_PASS: YES/NO`
  - [ ] `IS_PASS: NO` → 修复后复审（最多 2 轮）
  - [ ] 前端 `tsc`/构建通过、后端可导入启动
- 出口条件：`IS_PASS: YES` + 生成代码摘要

### 阶段 4 · 测试验证（QA 工程师 严过关）
- 输入：代码实现 + 架构设计中的验收标准
- 动作：为核心模块（权限/额度/注册确认/网关路由）编写并运行测试
- 智能路由判定（每轮必须做出）：
  - 源码有 Bug → 路由回工程师修复
  - 测试代码有 Bug → QA 自行修复
  - 全部通过 → 报告成功
- 迭代上限：**最多 2 轮**（第 1 轮发现问题反馈修复，第 2 轮回归验证；仍不过则输出报告标注遗留问题）
- 出口条件（G4 门禁）：核心用例通过率 100%，或遗留问题带清单与影响说明

### 阶段 5 · 交付汇总（主理人）
- 汇总 TL;DR、交付概览、文件清单、下一步建议
- 遗留问题与已知限制显式列出

## 4. 质量门禁总览（Quality Gates）

| 门禁 | 位置 | 裁定人 | 通过标准 |
|------|------|--------|---------|
| G1 | PRD 完成 | 主理人 | P0 明确、页面完整、无阻塞歧义 |
| G2 | 架构完成 | 主理人 | 任务列表可直接派发、接口契约明确 |
| G3 | 代码完成 | 工程师自检 + 主理人复核 | `IS_PASS: YES`、构建/启动通过 |
| G4 | 测试完成 | QA 判定 | 核心用例 100% 通过或遗留清单化 |

---

## 5. 沟通与反馈规则

1. **信息中转**：成员产出 → 主理人汇总 → 转交下一成员（附带完整上下文）。
2. **反馈回路**：
   - QA 发现源码 Bug → 附具体错误信息与失败用例 → 工程师修复
   - 架构师发现 PRD 歧义 → 回退产品经理澄清
   - 工程师发现设计问题 → 回退架构师修订
3. **语言一致**：所有输出使用与用户原始需求相同的语言（本项目为简体中文）。
4. **变更管理（增量开发）**：在已交付版本上提出新需求时，走增量流程 —— 增量 PRD → 增量设计 → 最小变更实现 → 全量回归 + 新功能测试。

canvas-studio/

│   ├── 04-test-report.md       # 测试报告（QA）

├── backend/                    # FastAPI 后端（可独立部署）

命名规范：
- 文档：`NN-<name>.md`（NN 为阶段序号）
- 源码：遵循各语言社区规范（TS: kebab-case 文件 + PascalCase 组件；Python: snake_case）
- 环境变量：`CS_`（canvas-studio）前缀做业务配置，集成服务变量沿用其原生名

## 7. 交付验收标准（Definition of Done）

一个功能被认定「完成」需同时满足：
1. 功能实现与 PRD 的 P0 描述一致
2. 通过 G3 一致性审查与 G4 测试门禁
3. 有可复现的启动/部署方式（文档化）
4. 暗黑模式 / i18n / 响应式（若涉及 UI）三件套齐备
5. 线上环境切换项（sub2api 真实 URL+Key、chatgpt2api 地址）全部走配置，不硬编码
6. **文档已产出**（见下方第 8 条，铁律）

## 8. 交付文档制度（铁律）

> **每完成一个需求 / 一个大功能，必须产出文档，并在 `DEV-LOG.md` 追加时间线记录。**
> 未写文档的功能，视为**未完成**，不允许交付给用户测试。

### 8.1 两层文档结构

| 层级 | 文件 | 维护方式 | 内容 |
|---|---|---|---|
| **总日志** | `docs/DEV-LOG.md` | **只追加，不删改** | 按时间倒序记录：什么时候干了什么、完成什么、改了哪些文件、验证结论、遗留项 |
| **专题文档** | `docs/changes/YYYY-MM-DD-<功能名>.md` | 每次新建 | 该功能的完整技术档案 |

### 8.2 专题文档固定结构（六段式）

```markdown
# <功能名称>

- **日期**：YYYY-MM-DD HH:MM–HH:MM
- **严重级别 / 模块**：P0-P2，涉及文件路径
- **一句话**：这段改动做了什么

## 一、背景与现象
## 二、排查路径        ← bug 类必写；每步「操作 → 结果」
## 三、根因            ← bug 类必写；多个根因要分条列明
## 四、修复方案        ← 或「设计方案」
## 五、改动文件清单     ← 表格：文件 | 改动
## 六、验证            ← 写实测数据，不写「已验证」这种空话
## 七、遗留与运维提示   ← 怎么排查、怎么规避、还有什么没做完
```

### 8.3 记录粒度标准

- ✅ **算一个功能块**：一个完整需求闭环、一次系统性 bug 修复、一个可独立验收的能力
- ❌ **不算**：单行文案修改、样式微调、refactor 中间态
- 一个功能块内如果有**多个独立根因**（像 2026-10-16 的生图链路），全部写进同一份专题文档，但根因要分条列清

### 8.4 反面教材（真实踩过的坑）

> 2026-10-16 的右栏截断问题：第一次只加了 `overflow-hidden`，溢出确实不外溢了，但内容依然超宽被裁掉 —— **遮丑不是修复**。
> 记录教训时要写清楚「第一次为什么错」，避免同类问题重复发生。

### 8.5 临时调试代码登记

排查期加的钩子（如 `window.__canvasApi`）、调试日志，必须在专题文档的「遗留」段落登记，并标明发布前需移除。
