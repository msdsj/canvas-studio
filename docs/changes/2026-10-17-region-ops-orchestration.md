# 选区局部编辑编排（Region Ops Orchestration）

> 日期：2026-10-17 · 状态：已落地 · 对标：lovart.ai 的智能选区编辑

---

## 一、要解决的问题

用户对图片的诉求天然是**混合**的：一张图上往往同时存在「这块改样式」和「那块抠出来」。
此前平台只能做前者，且动作类型写死在代码里，每来一种新玩法就要改一次代码。

四条产品硬要求：

| # | 要求 | 状态 |
|---|------|------|
| 1 | 仅改选中区域，其余像素完全保留 | 已有（合成保真），本轮沿用并加固 |
| 2 | 只改样式 → 产出 **1 张**完整修改图 | 已有 |
| 3 | 改样式 + 抠图混合 → 产出 **1 张**完整修改图 + **N 张**透明背景素材 | **本轮新增** |
| 4 | 产出严格对应选区，不越界 | 本轮加固（越界夹取 + 单测覆盖） |

同时解决两个架构问题：

- **能力不能写死**：不同用户场景差异极大（换装、抠图、去水印、扩图、换底、转绘、商品图白底……），
  能力必须可插拔；
- **用户不该背枚举**：用户只说人话，由 LLM 把需求解析成结构化计划。

---

## 二、架构：能力注册表 + 意图分析

```
用户原话 ─┐
          ├─→ 意图分析（LLM + 能力清单）─→ Intent DSL ─→ 编排器 ─┬─→ 整图类 ─→ 产出1（合成图）
框选区域 ─┘                                                      └─→ 素材类 ─→ 产出2..N（透明素材）
```

### 2.1 能力注册表（`edit_handlers.py`）

一种能力 = 一条声明，**新增能力不需要改任何执行代码**：

```python
EditHandler(
    id="cutout",                        # 能力标识（LLM 与前端引用）
    label="抠出为透明素材",              # 面向用户的中文短名
    description="把该区域的主体从背景中精确分离，输出透明背景的独立素材图片……",  # 给 LLM 看
    engine="local",                     # upstream=消耗算力 / local=本地确定性处理
    output="sprite",                    # composite=整图 / sprite=独立透明素材
    per_region=True,                    # 每区域各产出一张
    billable=False,                     # 本地能力免费
    executor="cutout",                  # 本地执行器
)
```

内置能力：

| id | 名称 | engine | output | 每区域一张 | 计费 |
|----|------|--------|--------|-----------|------|
| `restyle` | 改样式/换内容 | upstream | composite | 否 | 是 |
| `cutout` | 抠出为透明素材 | local | sprite | **是** | **否** |
| `transparent` | 就地挖空变透明 | local | composite | 否 | 否 |
| `remove` | 去除物体 | upstream | composite | 否 | 是 |
| `enhance` | 画质增强 | upstream | composite | 否 | 是 |

**扩展方式（管理员在后台改配置即可，零代码）**：

配置项 `EDIT_HANDLERS` 填 JSON 数组，例如新增「转动漫风」：

```json
[
  {
    "id": "anime",
    "label": "转动漫风",
    "description": "把该区域转为日系动漫风格，保持构图与内容不变。适用于「动漫化」「二次元」等需求。",
    "engine": "upstream",
    "output": "composite",
    "per_region": false,
    "billable": true,
    "prompt_prefix": "将该区域转为日系动漫风格，保持构图、内容与人物特征不变。"
  }
]
```

保存后：LLM 的可用能力清单自动包含 `anime` → 用户说「把这块变成动漫风」即可命中。
前端能力下拉框也自动出现该项。

### 2.2 意图分析（`plan_service.py`）

`POST /api/generate/plan` 把「用户原话 + 框选区域」解析为结构化计划：

```json
{
  "reply": "区域1 换成红色连衣裙，区域2 抠成透明素材",
  "ops": [
    {"region_index": 1, "region": {"x":0.0,"y":0.0,"w":0.3,"h":0.5},
     "handler": "restyle", "prompt": "换成红色哑光棉质连衣裙，保持姿态与光影", "intensity": "fine"},
    {"region_index": 2, "region": {"x":0.6,"y":0.6,"w":0.3,"h":0.3},
     "handler": "cutout", "prompt": "", "intensity": "fine"}
  ],
  "outputs": [
    {"handler": "restyle", "kind": "composite", "count": 1, "region_indexes": [1]},
    {"handler": "cutout",  "kind": "sprite",    "count": 1, "region_indexes": [2]}
  ],
  "summary": "区域1 改样式/换内容；区域2 抠出为透明素材"
}
```

**容错设计**（LLM 不可靠是常态）：

- 回复带 markdown 围栏 / 前后说明文字 → 多策略抽取 JSON；
- 完全解析不出 → 走兜底计划（全部按 `restyle` + 用户原话）；
- LLM 臆造不存在的区域编号 → **直接丢弃**，绝不越界改动；
- LLM 给出未知能力 id → 回退到兜底能力。

前端拿到计划后可先展示给用户确认/微调，再带 `ops` 调 `/api/generate/edit` 真正执行。

### 2.3 提示词模板（`app/prompts/`）

| 文件 | 用途 |
|------|------|
| `intent_planner.md` | 意图分析系统提示词（含 `{{catalog}}` 占位符，运行时注入能力清单） |

覆盖优先级：`system_configs.PROMPT_INTENT_PLANNER` > `app/prompts/intent_planner.md` > 代码兜底。
占位符用 `{{name}}` 而非 `{name}`——模板里含 JSON 示例，`str.format` 会冲突。

## 三、产出规则

| 场景 | 产出 |
|------|------|
| 全部是整图类能力 | **1 张**：完整修改图，选区外像素逐像素保留原图 |
| 全部是素材类能力 | **N 张**：每区域一张透明背景素材（PNG + alpha，尺寸按主体收紧） |
| 两类混合 | **1 张**整图 + **N 张**素材（整图在前，便于前端直接取首图） |
| 无选区（整图编辑） | 1 张，结果即最终图 |

编排顺序固定为「先整图、后素材」：

1. 所有上游类整图能力**合并为一次**图生图调用（区域编号 = 红框编号），省时省钱；
2. 结果与原图按选区合成（选区外严格不变，内缘羽化过渡）；
3. 本地整图能力（就地挖空）在合成结果上就地叠加；
4. 素材类能力逐区域本地抠图。

**计费**：只对 `engine=upstream` 的能力计费。纯抠图/挖空的任务 `cost=0`。

## 四、抠图技术路线（`cutout_service.py`）

**核心决策：抠图不走上游文生图。** 上游会重绘像素，而用户要的是「原图那个区域的内容」。
抠图必须是**本地确定性处理**，逐像素保留主体。

三级策略，有则升级、无则降级，零硬依赖：

| 策略 | 依赖 | 质量 | 说明 |
|------|------|------|------|
| `rembg` | `pip install rembg` | 最佳 | u2net 深度学习前景分割 |
| `grabcut` | `pip install opencv-python-headless` | 好 | OpenCV GrabCut 交互式分割 |
| `chroma` | **纯 Pillow** | 可用 | 边缘采样背景色 + 自适应阈值（默认兜底） |

`chroma` 算法：选区四边最外 2px 视为背景 → 轻量 k-means 聚类出 1-2 个背景色（兼容纯色与
双色/渐变背景）→ 每像素取「到最近背景色的通道最大差」→ 按边缘噪声水平自适应定阈值 →
映射为软 alpha → 形态学开闭去噪 → 内缘羽化 → 向内收紧到主体包围盒。

**健壮性保护**：

- 前景占比 < 1% 判定为抠图失败 → 回退为「纯选区裁剪」，**绝不交付空白素材**；
- 处理范围严格限定在框选矩形内，绝不越界；
- 仅做向内收紧（trim），不向外扩张。

策略可通过配置项 `CUTOUT_STRATEGY` 指定（`auto` / `rembg` / `grabcut` / `chroma`）。

### 5.1 接口变更

| 接口 | 变更 |
|------|------|
| `POST /api/generate/edit` | **新增 `ops` 表单字段**（JSON 数组）；旧 `region` 保持兼容 |

```json

  "prompt": "换成红色连衣裙",
  "intensity": "fine"
}
```

### 5.2 新增配置项（系统配置表）

| Key | 默认值 | 说明 |
|-----|--------|------|
| `EDIT_HANDLERS` | `[]` | 自定义能力声明（JSON 数组），同 id 覆盖内置 |
| `CUTOUT_STRATEGY` | `auto` | 抠图策略 |
| `INTENT_PLANNER_MODEL` | `gpt-4o-mini` | 意图分析模型 |
| `PROMPT_INTENT_PLANNER` | `""` | 意图分析提示词覆盖（留空用内置模板） |
| `LLM_BASE_URL` | `""` | 可选的 OpenAI 兼容意图分析中转地址，通常填到 `/v1` |
| `LLM_API_KEY` | `""` | 意图分析模型 API Key（后台掩码保存） |
| `LLM_MODEL` | `""` | 意图分析模型名；留空使用请求/上游默认值 |

### 5.3 接入第三方 AI 中转站

平台通过网关调用上游，**上游需兼容 OpenAI 协议**：

| 能力 | 上游接口 | 配置项 |
|------|---------|--------|
| 文生图 | `POST {base}/v1/images/generations` | `CHATGPT2API_BASE_URL` / `CHATGPT2API_ADMIN_KEY` |
| 图生图/编辑 | `POST {base}/v1/images/edits`（multipart，含 `image` / `mask`） | 同上 |
| 普通对话 | `POST {base}/v1/chat/completions` | `SUB2API_BASE_URL` / `SUB2API_API_KEY` |
| 意图分析对话 | `POST {base}/chat/completions` | `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` |

在后台「系统配置」页填写 base_url、key 和模型后保存，平台会自动推送至网关内存即时生效
（后端 60s 周期同步兜底）。意图分析中转地址通常填到提供商的 `/v1` 路径，网关会在其后拼接
`/chat/completions` 和 `/models`。如果 `LLM_BASE_URL` 留空，意图分析会兼容回退到原有
`sub2api` 对话上游。

> 图生图必须支持 multipart 上传图片；若要 `n>1` 多图产出，文生图接口需支持 `n` 参数。

## 十、上线后修复（同一日）

### 现象

框选了「改样式」和「抠图」两个区域，画布上却只有 1 张图，抠图结果不见。

### 根因（两个问题叠加）

**根因 1：后端未重启，`ops` 被旧代码忽略。**

后端进程仍运行改动前的代码（`/api/generate/plan`、`/api/generate/capabilities` 路由不存在即为佐证）。
旧版 `/api/generate/edit` 不识别 `ops` 字段，只认旧的 `region`，于是所有区域一律按兜底能力
（改样式）处理 → 只产出 1 张。

**根因 2：前端只投递 `result_urls[0]`，却把任务标记为「已投放」。**

`WorkspaceView` 里有两条结果落画布路径，行为不一致：

| 路径 | 原行为 |
|------|--------|
| `tick`（占位骨架主路径） | ❌ 只投 `result_urls[0]`，随后 `markTaskPlaced` |
| `placeResults`（兜底补投递） | ✅ 遍历全部 `result_urls` |

主路径投完第一张就标记任务已投放，兜底逻辑据此跳过 → **其余结果被永久丢弃**。

### 修复

1. 抽出模块级 `placeTaskResults()`：逐张投递全部产出，每张按自身宽高比缩放
   （只缩不放，最大边 320），横向保持 40px 间距；
   两条路径统一走它，消除行为不一致。
2. `imageSize()` 辅助：读取图片真实尺寸，避免把竖长的素材强行拉成正方形。
3. ChatPanel 的「加入画布」同样改为遍历全部 `result_urls`，并在 `WorkspaceView` 侧用
   游标错开位置，避免多张结果完全重叠。

### 附带改进：提示词意图自动识别

即使产出正确，用户也可能因为「默认能力是改样式」而漏选抠图。现在输入提示词时按关键词
即时纠正能力选择（写「抠出来 / 去背景 / 做成贴纸」→ 自动切到抠图），并把选择权留给用户：

- 仅当用户**未手动指定过**该区域能力时才自动改写；
- 这只是**输入辅助**，能力清单仍完全来自后端注册表（管理员新增的能力不会被限制，只是不自动识别）。

同时本地处理类能力（抠图/挖空）的输入框改为「可选」，并标注「本地处理」标签——
此前该输入框会被整块替换掉，用户已输入的文字会突然消失。

### 验证

真实环境端到端（非 mock）：提交 `ops = [restyle, cutout]` 的混合任务 →

```
结果张数: 2
  [1] PNG RGB  (256, 256)                     ← 完整修改图，与原图同尺寸
  [2] PNG RGBA (70, 70) alpha范围=(0, 255)    ← 透明素材，尺寸收紧到主体包围盒
```

后端全量回归 **120 passed**，前端 `tsc --noEmit` 通过。

### 教训

> **重构公共出口时，必须逐个核对所有入口的契约。**
>
> 本轮的「只投第一张」在改动前是无害的（一个任务永远只产出一张）；
> 引入多产出后它立刻变成数据丢失。这类 bug 不会在类型检查或单测里暴露，
> 只有「新增能力 → 审查所有消费该数据的位置」才能拦住。
>
> 同理，**部署步骤本身是功能的一部分**：后端未重启时，前端的新参数会被静默忽略，
> 表现为「代码明明写了却不生效」。

## 十一、第三轮修复：抠图区域被上游改了样式

### 现象

一张图上框了 3 个区域：2 处改样式 + 1 处「抠出来」。
结果被抠的那块**在原图里也被改了样式**——用户要的是「原样拿出来」，不是「改一下再拿出来」。

### 根因

**根因 1：标记图给全部区域画了红框（技术缺陷）。**

标记图（发给上游的 `mask`）由前端 `buildEditPayload` 用**全部** `regions` 绘制。
于是上游收到「3 个红框 + 只说区域 1、2 怎么改」的图——红框是强烈的视觉指令，
上游会认为区域 3 也要动。**这是设计缺陷，与用户操作无关。**

**根因 2：意图识别不够精准（产品缺陷）。**

「抠出来」到底该走 `cutout` 还是 `restyle`，此前只靠前端一份本地关键词表判断，
覆盖有限；一旦没命中，该区域就按默认的「改样式」提交。

**根因 3（连带）：兜底计划会覆盖用户的手动选择。**

对话模型不可用时后端返回兜底计划（全部按改样式），前端不加区分地应用，
会把用户「手动选了抠图」的设置冲掉。

### 修复

**1. 标记图只标注「需要上游处理的区域」——后端自绘，不信任前端。**

新增 `generate_service._render_region_mask()`：按 `ops` 中 `engine=upstream` 的区域
用 Pillow 重绘编号红框（白描边打底 + 红色实线 + 编号徽章，样式与前端一致）。
只要带了结构化 `ops`，后端就**忽略前端传来的 mask**，从根上杜绝「抠图区域被画框」。
编号沿用区域原始序号，与指令里的「区域N」严格对应（跳过抠图区域也不会错位）。

前端 `buildEditPayload` 同步支持 `markIndexes`，只标注上游区域（双保险 + 无 ops 场景仍可用）。

**2. 意图分析接入对话模型（用户明确要求）。**

- 编辑层新增 **「AI 分析」** 按钮：把各区域描述交给对话模型，回填处理方式与规范化指令；
- **提交前自动复核一次**：先分析再生成，把「说要抠图却按改样式提交」拦在生成之前；
- 分析过程**可见**：按钮与生成按钮显示「分析中…」，输入区上方给出进行中文案；
- 分析失败**不阻断**：退回用户的手动设置，始终能提交。

**3. 提示词写入硬约束。**

`intent_planner.md` 新增「抠图类需求（最高优先级）」章节，明确：

- 抠图是「只产出独立素材」，**绝不允许在原图该区域做任何修改**，`prompt` 留空；
- 「抠出来 / 提取 / 做成素材 / 去背景」↔ 抠图；「挖空 / 掏空 / 擦掉留空」↔ 就地透明，
  **两者语义相反不可混用**；
- 给出反例（用户说「把小猫抠出来」，若返回 `restyle` 即错）。

`edit_handlers.py` 中两个本地能力的 `description` 同步强化，并互相点明区别
（能力描述会注入 LLM 提示词，是最直接的调优面）。

**4. 兜底计划不再覆盖用户选择。**

前端检测 `plan.demo === true` 时跳过应用并提示「AI 分析暂不可用」。

### 验证

真实环境端到端（3 区域：2 处改样式 + 1 处抠图）：

```
记录的操作: ['restyle', 'restyle', 'cutout']
产出预估: [('composite', 1), ('sprite', 1)]
上游返回张数: 2
产出1 完整修改图 256×256 —— 抠图区中心像素 (215,35,35) = 原图红色，未被改动 ✓
产出2 透明素材 PNG RGBA 70×70 alpha(0,255) ✓
```

新增 4 项单测：

| 测试 | 断言 |
|------|------|
| `test_render_region_mask_excludes_local_regions` | 抠图区域在标记图上无任何标记 |
| `test_render_region_mask_keeps_original_numbers` | 跳过抠图区域后，其余编号不错位 |
| `test_three_regions_two_restyle_one_cutout` | 3 区域场景：抠图区域在原图严格不变、指令不含区域3 |
| `test_cutout_region_untouched_even_if_upstream_returns_modified` | 上游把整图涂红，抠图区域仍被还原为原图 |

后端全量 **124 passed**，前端 `tsc --noEmit` 通过。

### 设计结论

> **「不许改」这类约束不能只写在提示词里，必须落到像素上。**
>
> 提示词能提高上游听话的概率，但**概率不是保证**。本方案用三层防护：
> ① 提示词约束（降低上游误改意愿）→ ② 标记图只圈上游区域（消除视觉误导）
> → ③ 合成阶段按选区还原（即使上游乱改也还原回来）。
> 只有第 ③ 层是确定性的，前两层是优化。

该端口未启动，因此分析会走兜底（表现为「AI 分析暂不可用」）。

无需改代码、无需重启（平台会自动推送网关）。

## 十二、第四轮：架构对齐（按用户要求重构）

### 用户反馈

> 「我全部的图片操作都是需要去把图片和文字提示词给到 gpt 啊」
> 「要做什么裁剪啥的全部的操作其实你是需要走图片中转站去生成图片」
> 「如果要搞多张图片你需要考虑到并发」
> 「我框选的地方你好像一直都没有精确啊」

### 三个真实缺陷

**缺陷 1（最严重）：mask 用错了 —— 这是「框选不精确」的确定根因。**

发给上游的 `mask` 参数传的是**不透明的红框标记图**。但 OpenAI `images/edits` 的语义是
**「透明区域 = 要修改，不透明区域 = 保留」**。传一张全不透明的图，等于告诉上游
**「整张图都要改」**——所以「只改选中区域」完全靠提示词碰运气，AI 改哪儿全看它心情。

**缺陷 2：抠图做成了本地处理，方向错误。**

用户明确要求所有图片操作都走中转站（图 + 提示词），而我用 Pillow 在本地抠。

**缺陷 3：多区域/多图串行调用，没有并发。**

### 重构后的架构

**① 每个区域并发单独调用一次上游（不再合并成一条指令）。**

| 项 | 旧 | 新 |
|----|----|----|
| 调用方式 | 所有区域合并成 1 次请求 | **每个区域 1 次独立请求，并发执行** |
| 位置约束 | 靠提示词 + 红框，AI 常跑偏 | **标准 inpainting 掩码，物理约束** |
| 耗时 | 累加 | ≈ 最慢的一个 |
| 并发上限 | — | `EDIT_CONCURRENCY`（默认 3，夹取 1~6） |

**② 每次调用携带三样东西：**

```
image ① 纯原图（不画标记，避免标记被画进结果）
image ② 单区域引导图（只标出本次要改的那一个框，不干扰其它区域）
mask     标准 inpainting 掩码：仅该区域透明 ← 「只改这里」的真正约束
```

**③ 抠图改为走上游**：`cutout` 的 `engine` 从 `local` 改为 `upstream`，
内置提示词「将主体从背景中完整分离出来，输出纯透明背景（alpha 通道）的图片；
主体的内容、细节、颜色、光影保持与原图完全一致」。

**④ 抠图透明兜底**（新增 `CUTOUT_LOCAL_FALLBACK`，默认开启）：
实测发现**多数第三方中转站会把 PNG 重新编码、丢掉 alpha 通道**，
于是「抠图」拿到的是带背景的不透明图。检测到素材无透明像素时自动改用本地抠图补一次。

**⑤ 计费按上游调用次数**：`cost = edit 单价 × 上游区域数`，真实反映号池消耗。

**⑥ 合成兜底**：`_paste_region()` 把每个区域的结果贴回底图，**区域外逐像素保留原图**。
即使上游无视掩码把整图重绘了，选区外也不会被污染。

### 验证（真实环境）

**3 区域并发（2 处改样式 + 1 处抠图）：**

```
成本: 24 (= 8 × 3，按上游调用次数计费) ✓
日志确认: 3 条 /gw/images/edits 并发发出（同一毫秒两条）✓
产出: 1 张完整修改图 + 1 张素材 ✓
抠图区中心像素 (215,35,35) = 原图红色，未被改动 ✓
```

**抠图透明兜底：**

```
上游返回不透明图 → 兜底后素材 PNG RGBA 70×70，alpha 范围 (0,255) → 真透明 ✓
```

### 顺带修复的配置问题

排查中发现意图分析一直走兜底，根因是**中转站配置有两处笔误**：

| 配置项 | 原值 | 修正为 | 原因 |
|--------|------|--------|------|
| `TEXT_API_BASE_URL` | `https://provider.example` | `https://provider.example/v1` | OpenAI 兼容端点需带 `/v1` |
| `INTENT_PLANNER_MODEL` | `gpt-4o-mini` | `gpt-5.4-mini` | 该上游不支持 `gpt-4o-mini`（返回 `model_not_found`） |

修正后直连测试已确认模型可用（不再 404），但**上游当时持续返回 429 限流**，
意图分析的实际效果待限流恢复后确认。

### 设计结论

> **「只改选中区域」不能靠提示词，要靠掩码。**
>
> 提示词只能提高 AI 听话的概率；**标准 inpainting 掩码是物理约束**。
> 之前的红框标记图是「视觉暗示」，掩码才是「规则」。
> 叠加合成阶段的逐像素还原，才形成确定性的三层保障。

> **拆分调用比合并调用更精确。**
>
> 合并成一条指令时，AI 需要在一次推理里同时理解「区域1、区域2、区域3」三处位置，
> 极易顾此失彼。拆开后每次只有一个目标、一个掩码，精度显著提升，
> 代价是并发调用（用并发把耗时压回单次水平）。

## 十三、第五轮：简化回「一次调用 + 标注图」

### 用户澄清

> 「我左边选定一部分区域去抠图，另一部分区域改颜色，这两个地方我框选了，
> 你就用画笔或边框包起来，提交给 GPT 的时候把我这张用边框线或画笔处理的图片丢过去，
> 给 AI 的是包含两个需求的提示词和这张有涂鸦的图片，就这么简单。」

**上一轮的「按区域拆分并发 + 标准 inpainting 掩码」是过度设计。** 用户要的是最朴素的方案。

### 最终架构（当前实现）

```
用户框选/涂鸦 → 前端合成「标注图」（原图 + 涂鸦 + 编号红框）
              → 一次请求：标注图 + 分点提示词 → 上游
              → 拿回结果
              → 只把选区内的结果贴回底图（选区外逐像素保留原图）
              → 整图在前、素材在后，落到画布
```

| 项 | 实现 |
|----|------|
| 上游调用次数 | **1 次**（不按区域拆分） |
| 传给上游 | `image①` 底图（原图+涂鸦）、`image②` 引导图（原图+涂鸦+编号红框）、`prompt` 分点指令 |
| 改样式区域 | 合并进同一条指令，结果贴回选区 |
| 抠图区域 | **不送上游重绘**，从原图精确抠出（保证「原样拿出来」），不计费 |
| 就地挖空 | 上游生成 + 本地 alpha 收口 |
| 产出顺序 | 整图在前、素材在后 |

**抠图为什么不送上游**：上游会重绘像素，而用户要的是「原图那块原样拿出来」。
送去重绘会改掉内容，与需求相反。这一步是本地确定性处理，也顺带省一次额度。

### 前端图片处理库评估

当前用**原生 Canvas 2D**（零依赖，`ImageEditLayer.tsx` + `canvas-helpers.ts`），已支持：
框选（多区域、编号）、画笔、橡皮、撤销/重做、导出标注图。

若要升级为更接近设计工具的体验，可选：

| 库 | 体积 | 适合场景 | 取舍 |
|----|------|---------|------|
| **fabric.js** | ~300KB | 对象模型：矩形/箭头/文字/自由绘制，可选中拖拽调整 | 引入后需重写编辑层，但框选可拖动改大小 |
| **konva / react-konva** | ~180KB | React 声明式画布，性能好 | 同样需重写，适合要做图层/变换的场景 |
| **perfect-freehand** | ~3KB | 只做手绘笔迹（压感、真迹质感） | **可增量接入**：替换现有笔迹生成逻辑，其余不动 |
| **cropperjs** | ~30KB | 纯裁剪 | 只需裁剪时用，与标注编辑不冲突 |

**建议**：先接 `perfect-freehand`（3KB，只提升画笔手感，不动架构）。
若后续要做「框选后能拖动/缩放/改大小」，再上 `fabric.js` 重写编辑层。

### 已落地：接入 perfect-freehand

`npm install perfect-freehand`（新增 1 个包，gzip 后约 3KB）。

改动：

| 文件 | 变更 |
|------|------|
| `canvas-helpers.ts` | 新增 `paintStrokePath()`：用 `getStroke()` 生成笔迹轮廓 → `Path2D` → `ctx.fill()`；`paintStrokes()` 改为复用它 |
| `ImageEditLayer.tsx` | `redraw()` 的笔迹绘制改为调用 `paintStrokePath()`，删除原 `quadraticCurveTo` 等宽线逻辑 |

**收益**：笔迹随移动速度自然变粗细、起落笔有锥形收口，接近真实马克笔；
实时预览与导出标注图共用同一函数，所见即所得。

**验证**：`tsc --noEmit` 通过，`vite build` 通过（9.5s）。

## 十五、修复 Demo 占位图中文变方块

### 现象

上游不可达时网关降级生成占位图，图上的提示词全是「▯▯▯」方块。

### 根因

`demo_service.placeholder_png()` 调用 `draw.text()` 时**没传 `font`**，
Pillow 用默认位图字体（`ImageFont.load_default()`），该字体只有 ASCII 字形，
中文全部落到缺字形的方框里。

### 修复

新增 `_load_font(size)`，按平台优先级加载系统中文字体并缓存：

| 平台 | 候选字体 |
|------|---------|
| macOS | PingFang.ttc / Hiragino Sans GB.ttc / Arial Unicode.ttf |
| Linux | NotoSansCJK-Regular.ttc / wqy-zenhei.ttc |
| Windows | msyh.ttc / simhei.ttf |

全部找不到时退回默认字体（英文仍可读，不会崩）。

同时改进排版：

- 字号随画布尺寸缩放（`width // 42` 等），小图上不挤；
- 换行从 `textwrap.wrap`（按字符数）改为 `draw.textlength` 按**实际字宽**换行，
  中英文混排不再溢出。

### 验证

生成 768×512 占位图，提示词「一只在雨天打伞的柴犬，扁平插画风格，柔和配色」
完整清晰可读。

### 顺带修的测试过时引用

网关重构把 `sub2api_*` / `chatgpt2api_*` 改名为 `text_*` / `image_*`，
`conftest.mock_upstream` 仍在替换旧名 `chatgpt2api_client`，导致 13 个测试报
`AttributeError`。已改为替换 `provider_client`（各模块逐个 patch），并修正
`test_demo.py`、`test_qa_gateway.py` 的字段名与健康检查响应 key。

修复后网关 **14 passed**；剩余 6 个失败与号池/健康检查的业务语义变更有关
（图像上游已改为中转站直连，不再依赖号池），需单独确认后处理。

| 画布容器 | 加 `m-2` + `rounded-xl` + `border-border/60` + 极轻阴影，做成**浮起的卡片** |
| 菜单栏 / 素材栏 / 安全区 | `bg-surface` → `bg-bg-subtle`，边框 `border-border` → `border-border/50` |
| 创作入口按钮 | 去掉边框，改 `bg-bg-subtle` + 圆角 + hover 变品牌色浅底 |
| 素材缩略图 | `border` → `ring-1 ring-border/60` + `hover:shadow-sm` |
| 对话结果卡片 | `border border-border bg-surface` → `rounded-xl bg-bg-subtle`（无边框） |
| 侧栏标题 | `text-xs font-medium` → `text-[11px] font-semibold tracking-wide text-text-tertiary` |

### 顺手修的显示 Bug

对话卡片右上角的「演示结果 / 未查看」徽章被挤成**竖排单字**。
根因：标题 `truncate` 没有 `min-w-0 flex-1`，把徽章压到只剩一个字宽。
修复：标题加 `min-w-0 flex-1`，徽章组包一层 `shrink-0`，并给 `Badge` 基础样式加
`whitespace-nowrap` 根治。

### 设计原则

**用背景色分层，而不是用边框线分割。**
原来的界面每个区域都有一条 `border`，加起来七八条竖线横线，视觉很碎。
现在改成：浅灰（侧栏）↔ 白（对话/画布卡片）交替，只在必要处留 `border-border/50`。
