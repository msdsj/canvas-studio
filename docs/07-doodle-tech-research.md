# 图片涂鸦编辑功能 · 技术调研与选型结论

> 日期：2026-10-16 · 结论先行：**采用原生 Canvas 2D 实现，零第三方运行时依赖**

---

## 一、需求拆解

| 能力 | 说明 |
|------|------|
| 自由绘制 | 在图片上手绘笔迹（鼠标/触屏），带平滑与压感模拟 |
| 标注 | 颜色/粗细可选，便于圈画重点区域 |
| 撤销/清空 | 撤销单笔、清空全部 |
| 提交 | 合成「原图 + 涂鸦」为一张图提交上游，指令纯透传 |
| 尺寸预览 | 右栏实时显示提交图的真实像素宽高 |

## 二、第三方依赖库评估

| 方案 | 体积 | 手绘笔迹质量 | 撤销/清空 | 上手成本 | 结论 |
|------|------|-------------|----------|---------|------|
| **原生 Canvas 2D + Pointer Events** | **0 KB** | 中（lineCap/lineJoin round + rAF 合并已足够顺滑） | 需自研（笔画栈，~50 行） | 无 | ✅ **采用** |
| `perfect-freehand`（Google） | ~3 KB | **极佳**（速度/压感真迹算法） | 需自研（它是笔迹生成器，不含管理） | 低 | 备选：可后接入提升笔迹质感 |
| `signature_pad` | ~10 KB | 好 | 内置 | 低 | 偏"签名"场景，不适合多色标注 |
| `fabric`（对象画布） | ~300 KB | 一般 | 内置 | 中高（对象模型重） | ❌ 体积过大，功能过剩 |
| `konva` / `react-konva` | ~180 KB | 一般 | 内置 | 中 | ❌ 图形对象库，本需求用不上 |

**选型理由**
1. **零依赖风险**：不引入构建期不确定性（体积/版本/SSR 兼容），前端包体零增长；
2. **性能可控**：绘制直写 canvas（不经 React state），rAF 节流 → 120fps 级别响应，无卡顿；
3. **需求匹配**：本场景是"短笔画 + 圈注"，不需要对象模型/图层的编辑能力（fabric/konva 的强项）；
4. **可平滑升级**：笔画数据结构（points/color/width）设计成通用格式，将来若要接 `perfect-freehand` 只需替换"点生成"逻辑，其余不动。

## 三、核心设计

### 笔画数据结构（与库无关）
```ts
interface DoodleStroke {
  points: Array<{ x: number; y: number }>  // 原图坐标系（与分辨率无关，缩放不失真）
  color: string
  width: number                              // 原图坐标系线宽
}
```

### 坐标与分辨率策略
- 画布显示层按容器尺寸缩放；**所有笔迹坐标存储在原图坐标系**（提交时 1:1 渲染到原分辨率），因此任何缩放下笔迹都精确贴合；
- 提交时以**原图分辨率**离屏合成 → 上游拿到的图与原图完全同尺寸。

### 区域（region）推导
- 涂鸦笔迹的**包围盒**（bbox）自动作为编辑 region（归一化）→ 服务端框外合成保真继续生效。

### 性能要点
- `pointermove` 事件写入 canvas，不进 React state；
- 单指轨迹用 `requestAnimationFrame` 合并，避免高频重绘；
- 撤销/清空才触发整层重绘（redraw）。

## 四、提交流程

```
涂鸦完成 → 按原图分辨率合成（原图 + 笔迹）→ 与用户指令一并提交
   → POST /api/generate/edit（file=合成图, region=[bbox], prompt=用户指令原样透传）
   → 画布出现骨架屏占位 → 完成后原位渲染结果
```
