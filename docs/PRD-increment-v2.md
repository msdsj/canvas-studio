## 1. 现状差距与本次迭代目标

### 1.1 现状差距（代码核查结论）

| 用户诉求 | 核查结论 | 差距定性 |
|---|---|---|
| ① 中转站返回格式异常，需重试 + 备用模型 | `relay_service.chat()` 只在「HTTP ≥400 且报错文本含 `response_format`」时去掉 `json_mode` 重试一次（`relay_service.py:468`）。**响应体 `json.loads` 失败直接抛 `AppError`，无重试**（约 `relay_service.py:493-498`）；**无备用模型链**；对「返回 HTML / 纯文本 / 空体 / JSON 被截断 / 顶层非 dict」没有分类识别与降级。 | 传输层缺韧性 |
| ② 生图配内置 skills 模板 + 严格输出格式约束 | `design_skills.py` 已有 16 类 78 条技能（含 `prompt_scaffold / negative / aspect / style_tags / slots / pitfalls`），`compose_service` 用 `shortlist_skills()` 召回后注入提示词。**但没有强制输出 schema 契约**：模型返回的 `skill_id` 靠 `design_skills.get_skill()` 后置校验，取不到就丢弃、回退到 `shortlisted[0]`（`compose_service.py:697-701`）。格式漂移时**只能丢弃、不能纠偏**。 | 缺「契约 + 校验 + 自动修复」 |
| ③ 移除 AI 回答的边框包裹，参考 Lovart | AI 消息**气泡本身已无边框**（`ChatMessage.tsx` AI 分支只有 Avatar + Markdown，无 border/ring）。真正的「边框感」来自 AI 侧 8 处卡面组件统一使用的 `ring-1 ring-inset ring-border-faint` + `bg-surface` + `shadow-sheet`：`SkillRunCard:100`、`AnalysisSteps:40`、`ThinkingTrace:154`、`GenerationResultCard:103`、`ConfirmCountCard:74`、`EditCompareCard:20`、`LatestResultDock:130`、`ChatPanel:1428`；Markdown 内 `blockquote` 用左边框、`hr` 用横线（`Markdown.tsx:13,19`）。另核查：三栏之间**未使用** `border-l/r` 描边，`--color-gutter` token 目前也未被任何组件消费——分栏线不是「包裹感」来源。 | 边框在「子组件」不在「气泡」 |
| ④ 补齐边框线、标记标注、套索 | 编辑层**已有** `region / lasso / brush / pen / eraser` 五工具（`ImageEditLayer.tsx:56,1730-1762`）。**真正缺的是**：矩形/圆形**描边标注（边框）**、**箭头/序号/文字标签（标记）**。套索虽在，但属"有而难用/难发现"——工具条只有图标 + 极短 tooltip，无快捷键。 | 缺 2 个工具 + 1 个可用性复核 |
| ⑤⑥ 画布美化、整体体验升级 | 画布已有浮动工具岛（`CanvasToolbar.tsx`，底部胶囊 + Excalidraw 原生缩放岛）、纸/墨/青柠 token 已落地（`tokens.css`）。差距在**画布内部的视觉细节**：内容贴边、图片无统一投影、选中态沿用 Excalidraw 默认、空白画布无引导。 | 视觉打磨 + 一致性 |

**关键判断**：诉求①的根因在**传输层**（响应体不是 JSON），不在业务层。业务层 `compose_service._call_json()` 已有 1 次「追加纠错提示后重试」，且 `_extract_json()` 能容忍围栏与前后说明——这层容错**不覆盖**「HTTP 响应体本身是网页/空体」。本次必须在传输层补韧性，否则业务层的重试只是在拿同一条坏管道重试。

## 2. 用户故事

**诉求① 中转站韧性**
- 作为**正在赶稿的设计师**，我希望中转站抽风（返回网页/空响应/超时）时系统自动重试并换一个模型继续，以便我不用懂"JSON"是什么也能把图做出来。
- 作为**平台运营**，我希望每一次上游失败都留下"试了哪个模型、为什么失败"的记录，以便判断是用户配置问题还是上游问题。

**诉求② 输出契约**
- 作为**产品使用者**，我希望 AI 出的方案结构稳定（必有画面描述、比例、负向词、技能），以便我确认后建的任务与我在对话里看到的一致。
- 作为**开发**，我希望所有 AI 结构化输出走同一份 schema 定义，以便改字段时只改一处、测试有唯一断言基准。

**诉求③ 去边框**
- 作为**长期用户**，我希望 AI 的回答像一位设计师在白纸上跟我说话，而不是一堆灰框卡片，以便阅读时注意力落在内容上而不是容器上。

**诉求④ 编辑工具**
- 作为**电商运营**，我希望用矩形/圆形把"这块要改"圈出来、用箭头和序号指出"第 1 处、第 2 处"，以便一次说清多处修改而不用来回描述坐标。
- 作为**新手**，我希望每个编辑工具都有名字、快捷键和一句说明，以便我知道套索能圈不规则区域、而不是只用矩形。

**诉求⑤ 画布美化**
- 作为**每天泡在画布上的用户**，我希望画布像一张摆好的工作台（留白、投影、选中反馈清晰），以便长时间工作不觉得界面"廉价"。

**诉求⑥ 企业级梳理**
- 作为**团队负责人**，我希望功能按 P0/P1/P2 分批交付、边界写清楚，以便我能判断"这一版能不能给团队用"。

## 3. 需求池

> 优先级：**P0** = 阻塞主流程 / 影响数据正确性；**P1** = 体验显著受损；**P2** = 增强项。
> **P0 口径说明**：编辑工具（R07/R08）与去框（R11/R12）均为用户 6 项诉求中**明确点名**的内容，改动小、风险低，属本期交付主线而非增强，故统一列 P0（主理人裁决 4）。

| ID | 需求 | 优先级 | 验收标准（可验证） | 涉及端 |
|---|---|---|---|---|
| **R01** | 传输层响应体格式识别与同模型重试 | P0 | 上游返回 `text/html`（含 `<!doctype`/`<html`）、空体（0 字节）、顶层非 dict、JSON 截断（`json.loads` 报 `Unterminated`）四类中任一：系统在同一模型上自动重试 1 次（`temperature` 下调，间隔 ≤ 1s），日志记录 `attempt=1, reason=html_body｜empty_body｜not_object｜truncated_json`；连续 2 次失败进入 R02；用户侧报错文案**不含** `json` / `JSONDecodeError` / 异常堆栈。**重试全程不涉及配额变更**（口径见 3.1-R01） | 后端 |
| **R02** | 备用模型 fallback 链（**双层**） | P0 | ① **provider 内模型链**：中转站配置「备用模型」为可增删的有序列表（0–3 个），主模型失败按序切换，最多切换 2 个；② **provider 间互备**：本 provider 全链失败后，取该用户其他 provider（`updated_at desc`）作为二级候选，最多再试 1 个；③ 每次尝试写入调用记录（provider / 模型名 / 耗时 / 失败分类，**不含 Key**）；④ 全部失败时错误文案列出"已尝试：A → B → C"；⑤ 硬上限：**模型槽位 ≤ 4 个**（主模型 1 + 模型链 ≤ 2 + 跨 provider ≤ 1），**且总 HTTP 调用 ≤ 5 次**（4 槽位 + 主模型那 1 次 R01 重试），达上限立即终止；**重试权只给 slot 0（主模型）**，链上模型失败即切下一个槽位、不再重试（计数口径见 3.1-R02） | 后端 + 配置 |
| **R03** | 上游格式异常的统一错误语义 | P0 | 格式类错误必须包含 3 要素并透传到前端错误卡：① 现象（"上游返回了网页而不是数据"/"输出被截断"/"上游没有正文"）② 已尝试（模型 × 次数）③ 下一步（调大最大输出 tokens / 换模型 / 检查地址是否填成网页）；错误卡提供「换模型重试」按钮，点击即用同一需求重发，用户无需重填 | 后端 + 前端 |
| **R04** | 结构化输出契约（单一来源） | P0 | 新增 compose 编排的 schema 定义（字段名、必填、类型、枚举、长度上限），被 analyze / reason / prompt 三个阶段共用；`aspect` **契约层保留 5 值**、**UI 只暴露 3 档 `方形 1:1` / `竖版 2:3` / `横版 3:2`，界面显示的比例 = 实际产出比例、契约值不对外暴露**（映射表见 3.1-R04，唯一真源）；**label 固定三档、机型不支持时置灰不改文案**；`final_prompt ≤ 1500` 字符为**契约上限**，超长**不走纠错重试**、由本地 `smart_truncate()` 逐级截断（见 3.1-R04）；schema 导出的字段名集合与前端实际消费字段名集合有断言用例（集合相等），字段变更只改一处 | 后端 + 前端 |
| **R05** | 契约校验失败 → 自动修复重试 → 模板兜底 | P0 | **只有 5 类问题进纠错重试**：缺必填字段、类型错、枚举越界、`skill_id` 不存在、JSON 结构不合规（**超长不在其中**，见 3.1-R05）；重试时把「错误清单（字段路径 + 期望）」拼进下一次请求，最多修复 2 次；3 次仍不合法则用模板兜底产出（标记 `source=template_fallback`），**不阻塞建任务**；每次非法输出保留前 200 字符到日志；单测覆盖上述 5 类 + 「超长不得触发纠错」共 6 个用例 | 后端 |
| **R06** | 出图参数硬约束（技能默认值补齐） | P0 | 建任务请求必须满足：`aspect` 有值（plan 缺失时取命中技能的 `aspect` 默认值）、**`final_prompt` 尾部包含负向描述段**（见 3.1-R06，上游无独立负向参数）、`final_prompt` 长度 ≥ 40 且包含该技能 `style_tags` 中至少 1 个；任一项不满足则后端**拒绝建任务**并返回具体缺失项，不允许静默通过 | 后端 |
| **R07** | 边框线绘制工具（矩形 / 圆形描边） | P0 | 工具条新增「边框」；可选矩形/椭圆；拖拽绘制，可设颜色、线宽（细/中/粗）、实线/虚线；松手生成**标注对象**（不产生选区、不弹指令气泡，口径见 3.1-R07）；可拖动位置、可删除、可撤销重做；导出标注层时包含边框 | 前端 |

### 3.1 实现口径（按 ID 对应，含已裁决结论）

- **R01｜重试不涉及配额变更**：`quota_service.pre_deduct()` 发生在**建生图任务**时（`compose_service._dispatch`），文本编排（analyze / reason / prompt）本身不扣配额。因此传输层与契约层的重试**不产生任何用户账单变动**，不需要退款逻辑，也不存在"平台承担成本"的说法。注意与一期 §11.4 幂等口径一致：重试属同一次用户请求。
- **R02｜双层 fallback（不是二选一）**：
  - 第一层 **provider 内模型链**：`ai_providers` 新增 `fallback_models`（JSON 数组，0–3 个有序模型名），主模型失败后按序切换。
  - 第二层 **provider 间互备**：同用户的其他 provider（按 `updated_at desc`）作为二级候选，**不需要改表**——现有表已支持多 provider，只是过去只取 `is_active` 那一条。
  - 理由：只做模型链解决不了"整个中转站挂了"；只做 provider 链解决不了"同站某模型限流"。两层合起来才是用户说的"备用模型切换逻辑"。
  - **硬上限与计数口径（已裁决 D6）**：`MAX_MODEL_SLOTS = 4`（主模型 1 + 模型链 ≤ 2 + 跨 provider ≤ 1）+ `MAX_HTTP_CALLS = 5`（4 槽位 + 主模型那 1 次 R01 重试）。**重试权只给 slot 0**——R01 的"连续 2 次失败进入 R02"本就只描述主模型，链上模型按序切换、不重试。两个常量都必须硬编码，防止上游持续故障时把上游额度打穿；另设 `TOTAL_DEADLINE_S = 120` 兜底最坏延迟。
  - UI：中转站配置页「备用模型」做成可增删的有序列表（最多 3 个），下方一句说明"主模型失败时自动按顺序尝试"。
- **R04｜`aspect` 是双层，不是二选一（两层并存，不要统一成 3 值）**：
  - **契约层（模型输出）**：保留 5 值 `1:1｜3:4｜4:3｜9:16｜16:9`。模型需要能理解"竖版海报"（→ 9:16）与"人像特写"（→ 3:4）的语义差异，收窄到 3 值会让它丢失判断力。
  - **UI 层（用户手动选）**：只暴露 3 档——`方形 1:1` / `竖版 2:3` / `横版 3:2`。文案带"方形/竖版/横版"比纯数字更好认。
  - **唯一真源：契约值 ↔ 用户可见 label ↔ 实际尺寸**（主理人裁决；禁止在组件里硬编码比例字符串）

    | 契约值（内部，模型用） | 用户可见 label | 实际尺寸 | 实际比例 |
    |---|---|---|---|
    | `1:1` | `1:1` | 1024×1024 | 1:1 |
    | `3:4` | `2:3` | 1024×1536 | 2:3 |
    | `9:16` | `2:3` | 1024×1536 | 2:3 |
    | `4:3` | `3:2` | 1536×1024 | 3:2 |
    | `16:9` | `3:2` | 1536×1024 | 3:2 |

  - **一句话口径**：**界面显示的比例 = 实际产出比例；契约值是内部语义，不对外暴露。**
  - **事实依据**：`3:4 → 1024×1536`，而 1024:1536 = 2:3，不是 3:4；`4:3 → 1536×1024` = 3:2。显示 `3:4` 却产出 2:3，是用户量一下就会发现、并会当 bug 报上来的落差。
  - **所有用户可见处一律用 label**：比例选择器、方案卡、结果卡、导出信息。方案卡尤其不能显示 `9:16`——否则用户在确认环节看到 9:16、拿到 2:3，同一个落差会再出现一次。
  - **映射单一来源**：将来上游支持真 9:16 时只改上表一行，UI 自动跟随。
  - **label 固定三档；机型不支持时置灰，不改文案。** 三档文案（`1:1` / `2:3` / `3:2`）**永不随机型变化**；若某机型不支持某一档，按该机型 `supported_sizes` 计算可用性、**置灰该档** + tooltip「当前模型不支持这个比例」。本期三档全部支持，置灰逻辑存在但不触发（留作扩展位）。
    理由：① 同一句需求在不同机型下显示不同比例，用户会当 bug，且无法跨机型对照历史方案；② 更糟的是"切机型后已确认方案的比例突变"——用户已确认 2:3，切个机型变成 1:1，等于推翻他刚做的决定；③ 机型能力差异属**系统实现细节**，应由后端映射吸收，不该泄漏到 UI 文案层。置灰是可理解的限制，改文案是困惑。
  - **契约值的外露边界**：**方案卡 / 结果卡 / 导出信息 = 必须用 label**（硬要求，这三处是"承诺"）；**思考轨迹（`ThinkingTrace`）= 允许原文**（它是"过程"不是承诺）。`ThinkingTrace` 展示的是模型 `detail` 原文，模型很可能自己说"按 9:16 竖版构图"——**不要求改模型输出**，如需可在渲染层做一次 label 替换（`9:16`/`3:4` → `2:3`，`4:3`/`16:9` → `3:2`），成本高可先不做。
  - **映射按「图像模型」解析，不是按文本 provider**：文本 relay 的请求体里**没有 `size` 字段**（`_openai_body` / `_anthropic_body` 都不吃尺寸），所以文本层 fallback 换 provider **完全不影响 size**；真正决定 size 合法性的是图像模型——`size` 是传给 `create_image_task(model=model or "gpt-image-2", size=size)` 的（`compose_service.py:1152-1153 / 1165-1166`）。因此实现为 `resolve_size(aspect, image_model)`，第二维是**图像模型名**，配 `IMAGE_MODEL_SIZE_OVERRIDES` 覆盖表（按模型名覆盖 + `"*"` 通配）。不要做成裸常量，也不要挂在文本 provider 上。
- **R04｜长度上限：1500 + 本地截断（已按主理人裁决，原 800 / 纠错重试方案作废）**：契约上限 **1500 字符**；超 1500 **不进纠错重试**，走本地 `smart_truncate()`——按 `。！？` → `；` → `\n` → `，` 逐级降级切分，硬截断保底。`_MAX_PROMPT = 3800` 不动，作为上游安全阀（`verbatim` 路径是用户原话，不受 1500 约束）。截断事件需落日志（原长 / 截断后长度 / 降级到哪一级），供 R21 观测截断率。
  **为什么不用纠错重试（写进 PRD 备查，防止下一期改回去）**：① 超长的主因是**我们自己的技能模板撑长的**（`prompt_scaffold` + slots + 用户需求叠加），不是模型犯错——让模型"改短点"要重试 1–2 次、每次 5–20 秒，而它通常只是换个说法、长度没实质下降；② 超长是**确定性问题**，我们自己能截断，交给概率模型重试等于用 20 秒换一个仍然超长的结果；③ 纠错重试不可复现，会让 R05「3 次内 100% 通过」这条验收**无法测试**，本地截断可单测、可断言。
- **R05｜纠错重试的适用边界**：只有 **5 类**进纠错——缺必填字段、类型错、枚举越界、`skill_id` 不存在、JSON 结构不合规。**超长不在其中**（走 R04 的本地截断）。这条边界必须写进实现与测试，否则"超长也去重试"会同时污染 R05 的通过率指标和 R04 的延迟预算。
- **R06｜负向提示词不是独立参数**：平台上游**没有独立的负向提示词参数**，`negative` 是折进 `final_prompt` 尾部的（`compose_service.py:972` 注释、`:976` 拼装 `"{final_prompt}\n\n画面中避免出现：{negative}"`）。所以约束表述为「`final_prompt` 尾部必须包含负向描述段」，**不是**「请求里必须有一个 `negative` 字段」。校验实现应校验最终拼装后的提示词，而不是 plan 的原始字段。**并分两层**：① 契约层要求 `negative` 字段必填非空（模型必须产出它，失败走 R05 纠错）；② 出图前硬约束层对**拼装后**的 prompt 校验（尾部含负向段 + aspect 有值 + ≥ 40 字 + 含 style_tag），失败直接拒绝建任务。两层不可合并——①靠改 prompt 能救，②救不了（例如技能库没召回任何 skill 就没有 `style_tags` 可比对），合并会让"技能召回不准"被误判成"模型格式漂移"，白跑两次纠错还掩盖真实原因。
- **R06｜校验必须在扣费之前（硬要求）**：`quota_service.pre_deduct()` 发生在建生图任务时（`compose_service._dispatch` 内部调 `generate_service.create_*_task()`）。因此拼装 + 硬约束校验必须是**纯函数**且在 `_dispatch()` **之前**调用，绝不允许放进 `_dispatch()` 内部——否则会出现"校验失败但钱已经扣了"。需配两条机检：① `grep` 断言校验函数不在 `_dispatch()` 调用链内；② 单测 mock `pre_deduct` 断言调用次数 = 0（校验失败路径）。
- **R07/R08/R09｜标注不产出选区，但包围盒必须可见**：边框 / 标记与涂鸦（`pen`）同路径——只合成进参考图作视觉提示，**不产出选区、不参与掩码**。补充约束：**纯标注且无选区**时，以全部标注的包围盒作为修改区域，该包围盒必须在**提交前**以虚线框（`stroke-dasharray: 6 4`）+ 右下角尺寸标签（如 `320 × 180`）实时跟随显示在画面上，不允许黑箱提交。
- **R08｜序号用统一编号器**：标注不产生选区，因此不存在"与 regions 顺序对应"这个动作。实现为**统一编号器**——标注序号从 `regions.length + 1` 起算，删除不回收号码。既保证"规则一致"，又保证不与区域号撞号。
- **R11｜静态无框、交互有框，且分设备**：`pointer: fine` 设备用 hover 1px 描边作可点信号；触屏设备无 hover，改为**按压时浅底色**（`@media (hover: hover) and (pointer: fine)` 分档）。两者都只在交互态出现，静态态一律无描边。
- **R13｜验收方式**：文字标准人工核对 + 亮/暗双主题截图各一张留档；**不做像素 diff**（无设计基准图，先做基准图会多一轮返工，收益不抵成本）。

## 4. UI / 交互设计说明

### 4.1 诉求③：AI 回答区「去边框」后的层级表达

**原则：内容即界面。**

**范围（与 R11 对齐）**：AI 回答区**任何层级**都不再出现 1px 描边包裹——消息外层、过程块、结果卡、以及三栏之间的分栏线都在范围内。层级全部改由留白 + 底色差承担：`--color-gutter` 这个 token 的注释本身就是「工作台分栏缝隙：比画布再深一档，卡片才浮得起来」，设计意图本来就是用色差分区，而不是画线。

> **实现提醒（避免误诊）**：`index.css:18` 的 `--color-gutter: var(--color-gutter)` **不是**自引用 bug，它是 Tailwind v4 `@theme inline` 把设计 token 桥接成语义工具类（`bg-gutter`）的标准写法，同块内 20+ 个 token 都是这个形式。**不要删它**，删了 `bg-gutter` 直接失效。真正的问题是 `--color-gutter` 除桥接外全项目零引用——所以要做的是**在 `WorkspaceView` 三栏容器上加 `bg-gutter`**（R13 第 ⑥ 项），而不是删桥接。

层级由三样东西承担，按优先级：

1. **间距（主手段）**：块与块 16px，组与组 24px，话题之间 40px。相邻两块不再共用一个框，因此间距必须足够——16px 是下限，低于它两块会"糊成一段"。
2. **小标题**：12px、字距 0.12em、三级文字色、大写英文/中文短标签（如「思考过程」「方案」「结果」）。用文字当分隔线，而不是用线。
3. **字色与字重**：正文 15px/1.72 `--color-text`；次要说明 13px `--color-text-secondary`；元信息 12px `--color-text-tertiary`。数字、比例、参数用 mono。

**三处允许保留的视觉重量**（都不构成「1px 描边包裹」，因此不违反 R11）：

- **可交互卡片**（方案卡、澄清卡、结果卡）：静态**无边框、无阴影**，交互时才给反馈——`pointer: fine` 设备浮出 1px 描边 + `--shadow-sheet`，触屏设备改为按压浅底色（触屏没有 hover，靠描边会永远看不到）。静态无框、交互有框——边框从"装饰"变成"可点信号"。
- **结果图**：图本身即容器，保留圆角 + 投影（`--shadow-lift`），不再套外层卡片。
- **错误态**：保留左侧 2px 语义色条（danger / warning）+ 浅底色。这是"色条"不是"包围框"，且错误必须"看起来像错误"。

**Lovart 式适配要点**：留白要大（宁可多滚一屏，不要塞满）；不用分割线切块；过程类信息（思考轨迹、技能链）默认收成一行摘要，点开才展开——展开后也不加框，只用缩进 16px + 次级字色区分。

### 4.2 诉求④：两个新工具的位置与命名

**位置**：图片编辑层顶部工具条（`ImageEditLayer.tsx` 现有胶囊，`left-1/2 top-14`）。按 R15 重排为三组：

```
[ 框选 ][ 套索 ][ 画笔 ]  |  [ 标注 ][ 边框 ][ 标记 ]  |  [ 橡皮 ]   ·  颜色  粗细  撤销/重做
      选区组                      标注组                    擦除组
```

**命名与形态**：

- **边框**（图标：矩形描边）：点开后 popover 选「矩形 / 圆形」；线宽沿用现有 细/中/粗；样式 实线/虚线。语义是"把这块圈起来"。
- **标记**（图标：箭头）：点开后 popover 选「箭头 / 序号 / 文字」。序号自动递增，画面上渲染为小圆徽章（与现有选区编号徽章同规格，避免两套视觉）。文字标签点一下就地输入，≤ 20 字。
- 两者都归入**标注组**，与「标注（涂鸦）」同族——因为它们都只给上游做视觉提示，不产生选区、不弹指令气泡。这一点必须在 tooltip 里说清（"只做提示，不产生选区"），否则用户会以为能像框选一样填指令。
- 视觉：当前工具用青柠高亮；不可用的子选项置灰；组间 1px 分隔线（`--color-border`）。

**套索**：不新增图标位置，但补 tooltip「自由圈选不规则区域（L）」+ 快捷键，并在首次进入编辑层时给一次轻提示。

### 4.3 诉求⑤：画布区域视觉优化的着力点

| 着力点 | 具体做法 | 为什么 |

| **背景** | 点阵网格（`--color-canvas-dot`，24px 间距）+ 极淡纸纹（`--texture-paper`）；缩放 < 40% 时网格淡出 | 现在画布是纯色块，缺少"工作台"的空间感；点阵给对齐参考又不抢内容 |

## 5. 明确不做的事（范围边界）

1. **不做多页画布 / 版本树 / 分支对比**——本期只做单画布内的视觉与工具完善。
2. **不做多人实时协作**（光标、评论、权限）——架构影响大，单独立项。
3. **不引入本地像素级图像处理管线**（曲线、蒙版、图层混合）——抠图/透明仍走上游，编辑层保持"选区 + 指令"模型。
4. **不重写一期视觉语言**——`tokens.css` 的纸/墨/青柠三段结构不改，只做增量 token 与组件应用。
5. **不做技能库后台可视化编辑器**——技能仍随代码版本走（这是既有产品决策，避免后台一改全站风格漂移）；本期只加只读预览（R20）。
6. **不改计费与配额规则**——重试不涉及配额变更（已裁决 D2），本期不动 `quota_service` 的计费口径。
7. **不为新增/改动的 UI 追加移动端、平板适配**——本期只在 ≥ 1280px 桌面端验收；一期 P0-27 已交付的响应式断点**不得回归**（1440/1024/768/390 仍可用），但不要求新组件在这四档都做到最佳。
8. **不做"AI 自动改图并直接覆盖原图"**——仍保持"生成候选 → 用户确认"的链路。
9. **不做自有模型网关或更换上游**——继续用现有中转站抽象。

## 6. 已裁决事项

> 本节原为「待确认问题」，5 条均由主理人裁决完毕（D1–D5）；D6/D7 是架构评审中暴露出的两处口径冲突，由 PM 追加裁决。**开发按裁决执行，不再回头确认**；具体技术口径见 §3.1。

| # | 议题 | 裁决结论 | 落地位置 |
|---|---|---|---|
| D1 | 备用模型粒度 | **做双层 fallback，不是二选一**：① provider 内模型链（`ai_providers.fallback_models`，JSON 数组 0–3 个有序）② provider 间互备（同用户其他 provider 按 `updated_at desc` 作二级候选，**不改表**）。理由：只做模型链解决不了"整个站挂了"，只做 provider 链解决不了"同站某模型限流"。UI 为可增删有序列表（≤ 3）+ 一句说明"主模型失败时自动按顺序尝试"。 | R02、§3.1-R02 |
| D2 | 重试计费 | **重试不涉及配额变更**。`quota_service.pre_deduct()` 发生在建生图任务时，文本编排本身不扣配额，用户只为生图那一次付费。同时**必须硬编码重试上限**（计数口径见 D6），防止上游持续故障打穿上游额度。 | R01、R02、§3.1-R01 |
| D3 | 边框/标记是否产出选区 | **不产出选区**，仅视觉提示，与涂鸦（`pen`）同路径合成进参考图。补充：**纯标注无选区**时以全部标注的**包围盒**作为修改区域，该包围盒须在**提交前**以虚线框 + 尺寸提示显示，不允许黑箱。 | R07、R08、R09、§3.1-R07 |
| D4 | 去框范围 | **静态无框、交互有框**。补充：hover 描边只在 `pointer: fine` 设备生效；触屏改为**按压时浅底色**（触屏无 hover，靠描边会永远看不到）。**R11 / R12 由 P1 提为 P0**——用户第 3 项明确点名、改动小风险低，与 R07/R08 同属本期主线，优先级口径必须一致。 | R11、R12、§4.1、§3.1-R11 |
| D5 | 画布验收方式 | **文字标准 + 截图留档，不做像素 diff**：按 R13 的 5 条文字标准人工核对，交付时附亮/暗双主题截图各一张。不做 diff 的理由：没有设计基准图，先做基准图会多一轮返工，收益不抵成本。 | R13、§3.1-R13 |
| **D6** | **重试上限按「模型槽位」还是「HTTP 调用」计？**（原 R02⑤ 与 R01 存在算术冲突） | **按槽位计，调用数单列**：`MAX_MODEL_SLOTS = 4`（主模型 1 + 模型链 ≤ 2 + 跨 provider ≤ 1）+ `MAX_HTTP_CALLS = 5`（4 槽位 + 主模型那 1 次 R01 重试）；**重试权只给 slot 0**，链上模型失败即切下一槽位、不重试。取舍理由：R01 的同模型重试是用户第 1 项诉求的核心（"增加重试机制"），D1 的双层 fallback 是主理人裁决，两者都不能砍；能砍的只有"链上模型也重试"这个从未被要求的动作。另设 `TOTAL_DEADLINE_S = 120` 兜底最坏延迟。 | R02⑤、§3.1-R02 |
| **D7** | **`aspect` 5 值 / `final_prompt` 长度上限的口径** | ① `aspect` **双层并存**：契约层保留 5 值（模型需要理解"竖版海报"与"人像特写"的语义差异，收窄会丢失判断力），UI 层只暴露 3 档。**界面显示的比例 = 实际产出比例；契约值是内部语义，不对外暴露**——`1:1` / `2:3` / `3:2` 三项，映射表见 §3.1-R04（唯一真源，禁止在组件里硬编码比例字符串）。**label 固定三档；机型不支持时置灰，不改文案。** 外露边界：方案卡/结果卡/导出必须用 label，思考轨迹允许原文。映射按**图像模型**解析（`resolve_size(aspect, image_model)` + 覆盖表），不是按文本 provider（文本 relay 不收 `size`）。② 长度上限：**契约 1500 + 本地 `smart_truncate()`，超长不进纠错重试**；`_MAX_PROMPT=3800` 不动（上游安全阀）。**本条第 ② 点已按主理人裁决调整为 1500 / 本地截断，原「800 / 纠错重试 3 次后截断」方案作废**（理由见 §3.1-R04）。 | R04、R05、§3.1-R04、§3.1-R05 |

**附：一处技术事实（已写入 R06 口径）**——平台上游**没有独立的负向提示词参数**，`negative` 是折进 `final_prompt` 尾部的（`compose_service.py:972/976`）。因此分两层校验：**契约层**要求 `negative` 字段必填非空（模型必须产出它，失败走 R05 纠错）；**出图前硬约束层**对拼装后的 `prompt` 校验「尾部含负向描述段」。两层不可合并（详见 §3.1-R06）。另：该校验必须发生在 `pre_deduct()` **之前**，否则会出现"校验失败但钱已扣"（§3.1-R06 硬要求）。

**遗留风险（不影响开工，记录备查）**：D1 的跨 provider 互备会让「同一需求可能在不同 provider 上执行」，若不同 provider 的模型能力差异较大（如一个支持 4K、一个只到 1K），产出质量会有波动。本期接受该波动，不做能力对齐；若线上反馈明显，再考虑按「能力档位」过滤二级候选。
